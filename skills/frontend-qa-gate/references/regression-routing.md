# 回流路由表 (Regression Routing)

> 定位：验收发现缺陷后，**在哪里修、修完怎么重验**的静态契约。防止两类失控：把结构性缺陷当性能补丁就地修补（模式 1 浅层修补），或把代码级根因问题当作视觉问题反复重排。

---

## 1. 路由判定顺序 (Decision Order)

```text
缺陷出现
  ├─ 是否为方向级/品味级判断（该怎样表达、语气是否合适）？ → 升级人类创意总监裁决
  ├─ 根因在代码实现（hydration 失配 / 竞态 / 泄漏 / 类型与依赖）？ → 转 dual-round-review
  ├─ 需要在真实视口下重排信息层级或密度（结构类）？ → 回 taste-driven-designer D2
  └─ 其余产物行为缺口（行为修复类） → 就地修正 + 重验受影响断言
```

---

## 2. 路由表 (Routing Table)

| 缺陷类型 | 典型例子 | 修复位置 | 回流目标与重验路径 |
|---|---|---|---|
| **行为修复类** | 缺 `aria-label`、断点微调、焦点样式缺失、错误态未实现、加载态文案、触控目标过小 | 当前实现 | 就地修正 → 重跑受影响断言 → 无需重开设计阶段 |
| **结构类** | 真实视口下布局崩坏、需要重排信息层级或密度、组件拆分不合理导致状态错位 | 设计侧 | 回 `taste-driven-designer` **D2**（盲比记账后续跑）→ D3 后重新验收 |
| **根因类** | hydration 失配（模式 11）、异步竞态（模式 3）、资源/订阅泄漏（模式 5）、浅层修补掩盖状态失真（模式 1） | 代码侧 | 转 `dual-round-review` 按其裁定修复 → 回到本技能重验相关断言 |
| **方向级** | 错误态该怎样表达、空态语气、是否保留某装饰 | 创意总监 | 升级人类裁决并登记待决项；裁决前不得自行改动方向 |
| **安全类（超出范围）** | XSS、密钥进入产物、依赖投毒或错误包名 | 宿主 CI 与权限层 | 记录现象 + 标注「超出本技能范围」+ 升级 |

---

## 3. 与 dual-round-review 的接口 (Interface)

根因类缺陷转出时，报告必须提供使其可直接进入审查所需的最小上下文：

1. 现象与最小复现步骤（含网络/时序条件）；
2. 断言 ID 与失败证据路径；
3. 怀疑的实现范围（文件或模块级，不要求定位到行）；
4. 已排除的假设（避免审查者重复劳动）。

引用其失败模式库时**只引用编号与名称**（例如模式 11 运行时环境与 SSR 沙盒盲区、模式 3 隐蔽异步竞态、模式 5 资源与上下文泄漏），不复制其正文——该库的单一真相源在 `dual-round-review`。

---

## 4. 路由记录格式 (Routing Record)

报告的回流路由区块中，每条缺陷登记一行：

```text
| 断言 ID | 缺陷摘要 | 类型 | 修复位置 | 回流目标 | 重验断言 | 状态 |
```

- **状态**取值：待分流 / 修复中 / 已重验通过 / 已升级人类 / 超出范围；
- 同一断言连续 **2 轮**未通过且路由结论为「行为修复类」时，强制升级为结构类或根因类复核（避免就地修补循环）；
- 路由记录是交付说明的一部分，禁止只在会话中口头说明而不落盘。
