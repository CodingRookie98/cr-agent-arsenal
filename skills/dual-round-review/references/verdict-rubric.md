# 裁决分类与判定细则 (Verdict Rubric)

本细则定义双轮审查中的裁决分级、判别标准及处理动作，确保审查结论客观严谨，杜绝“讨好型盲从”与“过度挑刺阻碍交付”。

---

## 1. 裁决分类标准 (Verdict Categories)

| 裁决分类 | 标识 | 严重级别 | 核心定义 | 流程动作 |
| :--- | :--- | :--- | :--- | :--- |
| **阻断项** | 🔴 `Blocker` | **P0 / P1** | 经推演坐实的重大功能缺陷、安全漏洞、并发竞争、资源/连接泄漏、契约破损、或背离第一性原理的浅层打补丁。 | **强制阻断交付**。<br>必须在当前循环内实施精准修复并走 Scoped Delta 再循环（`delta-r1` 零缺陷时直接收口放行，否则入 R2 终审）。 |
| **优化建议** | 🟡 `Suggestion` | **P2 / P3** | 真实存在但不影响当前正确性、稳定性与外部契约的非阻断改进建议，或非本次引入的历史技术债。 | **允许放行交付**。<br>登记至项目待办清单（Backlog）或在后续迭代中安排，不阻断本次提交。 |
| **驳回项** | ⚪ `Dismissed` | **N/A** | 经第二轮架构师元审判证实属于第一轮的误报、幻觉、脱离实际上下文的臆想，或违反 YAGNI 的过度工程。 | **直接丢弃**。<br>在终审报告中附 `file:line` 反证据驳回，无需修改代码。 |

---

## 2. 级别判定基准 (Severity Levels)

### 🔴 P0 致命阻断 (Blocker - Critical)
* **核心特征**：系统崩溃、严重安全漏洞、数据丢失/破坏、或核心流程完全阻断。
* **典型场景**：
  * 注入攻击（SQL/命令/路径穿越）、越权访问、敏感凭据明文暴露。
  * 持久化迁移或写入逻辑导致已有数据不可逆丢失或静默损坏。
  * 主干链路未捕获的异步异常或空指针解引用导致进程崩溃。
  * 破坏公共 API 协议签名或不可逆规范契约，导致下游消费者失效。

### 🔴 P1 严重阻断 (Blocker - High)
* **核心特征**：核心业务逻辑错误、并发/异步死锁、资源泄漏、契约破损、运行时沙盒边界失效、或浅层掩盖真实根因。
* **典型场景**：
  * **浅层打布丁 (Palliative Patching)**：在外部加 `try/catch` 静默吞掉异常或早退掩盖错误，而不修复底层状态机不一致的根本原因。
  * **并发竞态 (Race Conditions)**：并发异步操作缺少取消令牌/清理逻辑或漏写 `await`，导致乱序状态覆盖或死锁。
  * **资源与句柄泄漏**：未清理的定时器、监听器、订阅、文件描述符或数据库连接。
  * **运行时与沙盒边界失配**：纯函数/初始化路径就地变异共享全局单例；受限沙盒/权限环境访问外部存储或文件缺少异常降级；跨端/SSR 渲染未隔离宿主全局对象或违规调用生命周期钩子导致水合/构建崩溃。
  * **测试造假与破坏隔离**：测试中自造 Fallback 数据绕过真实校验、伪造/弱化断言，或跨用例共享可变状态未做清理。
  * **关键边界未防御**：空集合/空值直接访问成员导致运行时异常。
  * **规范与契约文档硬缺陷**（适用于规范/规则/提案变更）：约束条款自相矛盾、引用不存在的文件/参数，或存在歧义足以导致读者按字面执行时越权或静默失效。

### 🟡 P2 重要优化 (Suggestion - Medium)
* **核心特征**：非致命的设计瑕疵、次要性能隐患、局部代码异味，不影响正常业务链路与外部契约。
* **典型场景**：
  * 局部重复逻辑可提取为小型纯函数但当前内联不影响正确性。
  * 次级路径缺少缓存或冗余开销导致的轻微性能损耗。
  * 局部弱类型未向外扩散。
  * **历史既有技术债**：在本次修改文件周边发现的、但非本次 Git Diff 写入的代码瑕疵。

### 🟡 P3 轻微改进 (Suggestion - Low)
* **核心特征**：命名建议、文档注释完善、微小的风格或可读性对齐。
* **典型场景**：
  * 标识符命名可更自解释（但符合项目既有风格）。
  * 注释或非规范性表述的清晰度优化。

### ⚪ 驳回分类 (Dismissed Patterns)
* **典型驳回场景**：
  * **越界历史考古挑刺**：R1 抓取未被本次改动破坏的历史既有代码，强行判定为 P0/P1 Blocker。
  * **缺乏上下文的误报**：R1 声称缺少鉴权或空值检查，但上游中间件、网关或 Schema 校验器已严格防御（须给出 `file:line` 反证据）。
  * **过度工程 (Over-engineering / Speculative Generality)**：针对单一明确场景，要求引入抽象工厂、插件体系等不必要间接层。
  * **次生风险过大**：建议推翻已稳定运行的公共模块引发级联破坏。
  * **与项目既有规范冲突**：主观偏好与仓库既有规则相左。

## 3. ⛔ Diff 范围边界裁决铁律 (Diff-Scope Boundary Rule)

为杜绝审查发散与历史代码越界挑刺阻断交付，审查与裁决必须严格执行以下红线。**审查范围**：当前 Git Diff 变更行及其直接紧邻调用（约上下游 5~10 行）；超出该范围的既有代码属于历史技术债。
1. **Blocker 准入资格**：只有**本次提交变更行（`git diff` 中的新增行或删除行）直接引入的缺陷**，或者**本次变更直接破坏了既有上下游正常调用**，方可被定级为 🔴 **Blocker (P0/P1)**。
2. **历史代码强行降级**：若某缺陷存在于旧有代码中，但**本次改动根本没有修改那几行代码**，该项**绝对严禁**作为阻断项。必须强制将其定级限制在 🟡 **Suggestion (P2/P3)** 记入待办，严禁阻断当前提交！

## 4. 裁决格式标准 (Verdict Output Schema)

**Light 模式**：同用下表 7 列结构，其中"原始 R1 评级"与"终审裁决"由同一裁决者填写（无 R2 对齐环节）。
**Scoped Delta 模式**：若 `delta-r1` 为 0 缺陷（空清单），主智能体可直接收口放行，免派发 `delta-r2`；若 `delta-r1` 存在待审项，须由 R2 按下表 1-to-1 定性裁决。

终审裁决明细表必须采用如下统一 7 列结构：

### 最终裁决明细表 (Final Verdict Synthesis Table)

| 稳定 ID (沿用 R1) | 检查点 / 文件位置 | 原始 R1 评级 | 变更归属 (本次引入/历史既有) | 终审裁决 | 最终定性分析与裁决理由 | 处置要求 |
|:---|:---|:---:|:---:|:---:|:---|:---|
| R1-1 | `src/auth.ts:45` | P0 | 本次引入 | 🔴 **P0 阻断项** | 确认存在未处理异常悬挂，高并发下导致进程退出。 | 必须修复，打回重测 |
| R1-2 | `src/utils.ts:12` | P1 | 本次引入 | ⚪ **驳回项** | R1 误判，反证据 `src/api/schema.ts:30` 已校验该字段。 | 丢弃，无需改动 |
| R1-3 | `src/legacy.ts:88` | P1 | 历史既有 | 🟡 **P2 优化建议** | 既有历史代码，非本次改动引入，越界定级被否决。 | 记入待办，准予放行 |
| R1-4 | `src/types.ts:8` | P2 | 本次引入 | 🟡 **P2 优化建议** | 命名可优化，不影响外部契约与逻辑，记入待办。 | 记入待办，准予放行 |

**交付判定**: [🔴 阻断交付 (Blockers > 0，精准修复后按模式再循环) | ✅ 准予交付 (Blockers == 0，允许提交并进入下一环节)]

> 交付门禁 `check-review-report.py --require-verdict=PASS` 校验归档索引 `README.md` 的 `**终审裁决**` 字段：须为 `准予交付` 或 `准予交付（<含数字的全角括号统计串>）`（支持可选前导 `✅` 与 `**` 加粗）。
