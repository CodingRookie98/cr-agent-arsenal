# 裁决分类与判定细则 (Verdict Rubric)

本细则定义双轮审查中的裁决分级、判别标准及处理动作，确保审查结论客观严谨，杜绝“讨好型盲从”与“过度挑刺阻碍交付”。

---

## 1. 裁决分类标准 (Verdict Categories)

| 裁决分类 | 标识 | 严重级别 | 核心定义 | 流程动作 |
| :--- | :--- | :--- | :--- | :--- |
| **阻断项** | 🔴 `Blocker` | **P0 / P1** | 经两轮推演坐实的重大功能缺陷、安全漏洞、并发竞争、内存/连接泄漏、契约破损、或背离第一性原理的浅层打补丁。 | **强制阻断交付**。<br>必须在当前循环内实施精准修复，修复后强制从 R1 重新走完整双轮闭环。 |
| **优化建议** | 🟡 `Suggestion` | **P2 / P3** | 经两轮验证属于真实存在但不影响当前正确性、稳定性与外部契约的非阻断改进建议。 | **允许放行交付**。<br>登记至项目待办清单（Backlog）或在后续迭代中单独安排，不阻断本次提交。 |
| **驳回项** | ⚪ `Dismissed` | **N/A** | 经第二轮架构师元审判证实属于第一轮的误报、幻觉、脱离实际上下文的臆想，或违反 YAGNI 的过度工程。 | **直接丢弃**。<br>在终审报告中陈述客观驳回理由，无需修复，防止代码被冗余设计污染。 |

---

## 2. 级别判定基准 (Severity Levels)

### 🔴 P0 致命阻断 (Blocker - Critical)
* **核心特征**：系统崩溃、严重安全漏洞、数据丢失/破坏、或核心流程完全阻断。
* **典型场景**：
  * SQL 注入、越权访问、未受保护的敏感凭据暴露。
  * 数据库迁移导致已有持久化数据不可逆丢失或静默损坏。
  * 主干链路未捕获的异步异常（Unhandled Promise Rejection）导致服务进程崩溃。
  * 破坏公共 API 协议签名，导致所有下游消费者构建或运行时崩溃。

### 🔴 P1 严重阻断 (Blocker - High)
* **核心特征**：核心业务逻辑错误、并发/异步死锁、资源泄漏、契约破损、React 生命周期破坏、或浅层掩盖真实根因。
* **典型场景**：
  * **React 生命周期与 Hook 违规**：在条件早退语句（`if (...) return`）之后调用 Hook，直接违反 React Rules of Hooks，导致构建报错（Lint Exit Code 1）或条件路由切换时客户端白屏崩溃。
  * **SSR 水合失配与无痕沙盒崩溃**：在客户端组件渲染阶段裸调用 `window` / `localStorage` 导致 SSR 水合失配，或在无痕模式/Cookie 受限环境下抛出未捕获的 `SecurityError`。
  * **全局渲染副作用污染**：在 React `useState` 初始化器或 render 纯函数中就地变异（`.push` / 原地属性覆盖）全局单例对象（如全局 Mock 数据源）。
  * **浅层打布丁 (Palliative Patching)**：在外部加 `try/catch` 静默忽略错误，而不修复底层状态机跳转不一致的根本原因。
  * **并发竞态 (Race Conditions)**：快速连续触发事件导致状态覆盖或竞态死锁；缺少取消令牌或清理函数。
  * **资源泄漏**：未清理的 `setInterval`、未注销的全局事件监听器、未关闭的数据库连接/文件句柄。
  * **测试造假与破坏隔离**：测试中自造 Fallback 数据绕过真实校验；跨测试用例共享全局可变状态且未做现场清理。
  * **关键边界未防御**：空数组/空对象直接访问属性导致运行时 `TypeError: Cannot read property of undefined`。

### 🟡 P2 重要优化 (Suggestion - Medium)
* **核心特征**：非致命的设计瑕疵、次要性能隐患、局部的代码异味，不影响正常业务链路。
* **典型场景**：
  * 局部重复逻辑（DRY），可提取小型纯函数但当前内联不影响运行。
  * 复杂度较高但有完备测试覆盖的控制流分支。
  * 次级网络请求未加缓存导致的轻微性能损耗。
  * 类型定义中存在局部的 `any` 或弱类型，但未向外扩散。
  * **历史既有技术债**：在本次修改文件周边发现的、但非本次 Git Diff 写入的代码瑕疵（如历史遗留 mock 数组、未抽象的旧常量等）。

### 🟡 P3 轻微改进 (Suggestion - Low)
* **核心特征**：命名建议、文档注释、细微的代码风格对齐。
* **典型场景**：
  * 函数或变量命名不够自解释（但符合项目既有风格）。
  * 遗留未更新的 JSDoc/注释。
  * 代码组织顺序（例如公共方法与私有方法的排列顺序）。

### ⚪ 驳回分类 (Dismissed Patterns)
* **典型驳回场景**：
  * **越界历史考古挑刺**：R1 抓取未被本次改动破坏的历史既有代码，并强判定为 P0/P1 Blocker（直接予以驳回或降级为 Suggestion）。
  * **缺乏上下文的误报**：R1 声称缺少参数校验，但该参数在 API 网关层已通过全局中间件严格验证。
  * **过度工程 (Over-engineering / Speculative Generality)**：针对只有一个实现类的工具函数，R1 要求抽象为插件工厂模式。
  * **次生风险过大**：R1 建议重构一个已稳定运行且缺乏改动理由的核心公共库。
  * **与项目既有规范冲突**：R1 根据个人偏好建议的风格与仓库已有的规则文件相左（仓库规则享有最高优先级）。

## 3. ⛔ Diff 范围边界裁决铁律 (Diff-Scope Boundary Rule)

为杜绝审查发散与历史代码越界挑刺阻断交付，第二轮元审判必须严格执行以下红线：
1. **Blocker 准入资格**：只有**本次提交变更行（`git diff` 中的新增行或删除行）直接引入的缺陷**，或者**本次变更直接破坏了既有上下游正常调用**，方可被定级为 🔴 **Blocker (P0/P1)**。
2. **历史代码强行降级**：若某缺陷存在于旧有代码中，但**本次改动根本没有修改那几行代码**，该项**绝对严禁**作为阻断项。第二轮架构师必须强制将其纠正降级为 🟡 **Suggestion (P2/P3)** 登记至待办，严禁阻断当前提交！
