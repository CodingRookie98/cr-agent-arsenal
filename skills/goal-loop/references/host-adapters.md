# 宿主执行后端适配与编排纪律 (Host Execution Adapters)

## 概述

`Execute`（原 P3）阶段的 TDD 实现可落在多种执行后端上。本规程定义**后端无关的能力契约**、**降级与超期收口规则**以及**现代执行自治纪律**，避免将技能绑定在单一厂商 CLI 或固定模型上。`goal-loop` 只要求能派发上下文隔离的执行单元并取回结构化结果。

---

## 1. 开工前：向用户确认后端 (Ask the User)

进入 `Execute` 前，主调度智能体必须先用宿主提问工具向用户确认执行后端，并按当前宿主实际检测结果裁剪选项：

| 选项 | 适用场景 | 说明 |
|---|---|---|
| **宿主原生子智能体** | 宿主具备子智能体/隔离工作区派发原语 | 上下文隔离最佳；优先推荐 |
| **外部无头 CLI** | 本机已安装支持非交互执行的编码 CLI（如 `agy -p` / `claude -p` / `codex exec`）且用户指定 | 使用 CLI 原生沙箱与自身模型配置，不硬编码具体模型名 |
| **当前会话内联** | 任务小、无需隔离，或前两者不可用 | 派发开销最低；长任务需严控上下文 |

**默认行为**：检测到几个可用后端就列几个选项，不预先假定；**严禁**在规程中写死具体品牌/版本号模型名，模型以所选后端自身配置或用户显式指定为准。

---

## 2. 后端能力矩阵 (Capability Matrix)

| 能力维度 | 宿主原生子智能体 | 外部无头 CLI | 当前会话内联 |
|---|---|---|---|
| 上下文隔离 | 强（独立会话/工作区） | 强（独立进程） | 无 |
| 结构化结果回传 | 可回传最终消息/文件 | 依赖 CLI 输出与落盘约定 | 无（同上下文） |
| 并行派发 | 视宿主原语而定 | 可并行后台批次 | 串行 |
| 适用粒度与主要风险 | 中~大；宿主差异 | 中~大；代理/OAuth/超时落盘延迟 | 小（约 2 分钟内）；上下文膨胀 |

> 无论选哪种后端，**输入规约**统一采用 [atomic-task-template.md](../templates/atomic-task-template.md)，**输出契约**统一采用其第 8 节。

---

## 3. 宿主能力映射 (Capability Mapping)

将规程中的抽象能力映射为当前宿主实际声明的工具（以会话工具清单为准，非硬绑定）：

| 抽象能力 | 典型宿主能力族 |
|---|---|
| 代码库检索与网页抓取 | `glob` / `grep` 与 `web_fetch` 等等价工具 |
| 会话进度跟踪 | 宿主原生步骤清单原语（如 `update_steps` / `TodoWrite`；仅作会话视图，跨会话真相源仍是计划头部 `Active Checkpoint`） |
| 隔离工作区子智能体 | 宿主原生 subagent / worktree / branch 隔离派发原语 |
| 工作流编排 | 宿主原生多阶段/扇出并行 workflow 编排原语（如适用） |
| 交互式提问 | 宿主的用户提问原语（仅主会话可用） |

## 4. 降级与失败处理 (Degradation)

1. 所选后端不可用（命令缺失、鉴权失败、宿主无原语）时，**立即向用户说明并切换至可行后端**，严禁静默替换；
2. 外部无头 CLI 异常退出、网络/OAuth 中断或超时时，先按 §4.1 验真再决定重试或降级；连续多批失控按 §4.2 止损切回前台直写；
3. 内联执行接近上下文上限时，先落盘检查点，再切隔离后端续跑；所有后端切换均写入计划 `Active Checkpoint`。

### 4.1 假失败与延迟落盘判别 (Silent Landing SOP)
外部无头 CLI 返回非零退出码时，流式写盘可能已完成、仅收尾汇报失败。**严禁直接重跑覆盖，必须先验真**：
1. 执行 `git status -s` 核对目标文件是否已落盘；高 I/O 环境下若首发为空，等待 5~10 秒复查一次，并仅清理本次新增未跟踪（`??`）的越权临时文档；
2. 直接运行该子任务对应的编译或单元测试验收命令（不重跑外部 CLI）；
3. **三态裁决**：产物完整且测试全绿 → 判为**假失败（Silent Landing）**直接验收；代码已编译通过仅漏写单测 → 保留已落盘代码并补齐测试，严禁整批重跑；产物残缺或编译破坏 → 判为真实故障，按 [failure-recovery-protocol.md](failure-recovery-protocol.md) 止血或切换后端。

### 4.2 切回前台直写的四条止损准则 (Direct-Write Criteria)
本节**仅适用于 `Execute` 非审查类执行子任务**（审查类严禁内联降级，见 §5.4(c)）。以下 **4 条同时满足**时，向用户说明后改由当前会话直写落地并记入检查点：
1. **高重写率**：连续 2 批及以上中 >50% 后台产出需整体重写；
2. **系统性错配**：同类结构错误（编造字段、放宽类型）跨文件反复出现；
3. **前台掌握全量上下文**：主调度已读完目标契约与夹具，掌握事实显著多于后台；
4. **剩余模块高度同质化**：完成首个样本后其余为机械化复刻。

## 5. 派发预算与等待纪律 (Dispatch Budget & Waiting Discipline)

> **预算单位是「轮次 / 检查点周期」，不是人类日历时间。** AI 执行时长不可预测，可收敛的只有派发次数、轮次与检查点周期。

### 5.1 派发即登记 (Register Before Dispatch)
派发任何子智能体前，必须在 `.goal-loop/dispatch-ledger.md` 登记派发账本明细（时间/轮次、角色 `R1 红队 | R2 元审判 | 执行子任务 <id>`、同角色同基线累计**派发次数**、后端与句柄、基线 SHA、状态 `等待中 → 已返回 / 已超期中断 / 已替代`），并在计划 `Active Checkpoint` 保留一行在途句柄派生摘要（会话重启后以计划摘要为恢复锚点）。

### 5.2 提示词自包含约束 (Self-Contained Prompt)
派发给子智能体的提示词**必须自包含全部决策与约束**，严禁要求子智能体运行时向人类提问（实测宿主会拒绝子智能体调用人类交互通道导致流水线挂死）。凡需裁决项必须在派发前给定，或按 `clarification-protocol` 转为显式默认假设。

### 5.3 等待预算 (Waiting Budget)
1. **同步派发**：当前回合等待并取回结果，等待期间严禁抢跑派发下一轮审查；若后端无法在调用内取回结构化结果，必须改用异步或可中断原语；
2. **异步派发**：记录句柄后结束当前回合，等待唤醒通知；
3. **预算上限与超期判据**：单次等待预算为 **1 个检查点周期**；**主调度主动探测 N 次（默认 2 次）均无新输出且句柄仍存活**，或句柄已死亡，任一成立即判为**超期事件**，按 §5.4 收口。

### 5.4 超期收口与替代路径 (Timeout Closure & Fallback)
超期事件按固定顺序串行收口并落盘：
1. **中断**：调用宿主中断原语终止挂死子智能体；
2. **记录**：将中断原因写入审查上下文或计划 Context Log；
3. **替代（仅限隔离合规路径）**：
   - **(a)** 原后端重派并收窄范围（受第 4 项重派上限约束）；
   - **(b)** 切换至另一隔离后端（外部无头 CLI 或等价可中断隔离原语）；
   - **(c)** 无法保证上下文隔离时，**审查类派发严禁内联降级——必须升级人类裁决**（作者自审不构成独立审查）；
   - **(d)** 非审查类执行子任务可在主会话内联收口，但必须标注「**本结果未经隔离验证**」且不得充当审查轮次；
4. **恢复与重派上限**：更新派发账本后再继续。同一角色对**同一基线**的重派上限为 **2 次**（每次超期中断计 1 次，且计入 `dual-round-review` 连续双轮循环计数）；触顶仍无产出即停止重派并按 [failure-recovery-protocol.md](failure-recovery-protocol.md) 升级人类裁决（中断无产出子智能体并如实记录不违反真实产出纪律）。

## 6. 多智能体并行编排 (Parallel Orchestration)

| 场景 | 编排规则 |
|---|---|
| 同文件写入任务 | **严禁并行**，合并为单任务顺序执行 |
| 无文件冲突的独立写任务 / 只读探查 | 批内可并行 |
| 全局构建 / 全量测试 / 级联审查（R1 → R2） | **严禁并行**；构建由主调度批末统一执行，R2 必须等待 R1 真实报告 |

**并行预算**：在途 `等待中` 子智能体上限默认 **3 个**；各在途任务独立计时，单笔超期不得冻结整批；多笔同时超期时收口与账本写入必须串行逐笔完成；批次结束逐条核对派发账本确认无遗漏终态。

## 7. 现代执行自治纪律 (2026 Orchestration Discipline)

1. **先裁决，不卡死（Rulings, not stalls）**：`Execute` 期间遇到非致命小歧义或计划微瑕疵时，主调度直接做出最小可逆裁决，在计划 Context Log 写入 `Ruling: <决策与依据>` 并继续推进；仅触及以下 **4 类硬停边界** 时必须停下请示人类：
   - ① 公共契约、对外接口或持久化 Schema 的破坏性变更；
   - ② 不可逆数据销毁、权限越界或安全红线风险；
   - ③ 触发 3-Tries 熔断且根因未收敛；
   - ④ 需求方验收口径与既有事实存在直接冲突。
2. **通用能力档位模型分层**：不写死具体品牌或模型名，按任务复杂度匹配能力档位——**高档**用于架构决策、复杂排障与独立对抗审查；**中档**用于标准功能实现与单测编写；**低档**用于机械批量替换、文档同步与只读检索。遵循 **「轮次成本优于单价（Turn count beats token price）」**：能用更强档位 1 轮精准收口时，勿用弱档反复拉扯多轮。
3. **同形小改动合批 + 禁套娃审查**：跨文件无冲突的同形微改合并为单次子任务派发，摊薄派发与验收成本；执行子智能体**严禁私自再派审查员**，独立审查权统一由主调度在 `Verify` 阶段行使。
4. **文件指针交接**：派发子任务或终审前，优先运行 `scripts/pack-handoff.py` 并通过 `--out .goal-loop/<file>.md` 生成独立交接文件（`brief` 抽取单任务简报、`review-pkg` 打包 `BASE..HEAD` 变更清单），向子智能体只传递**文件路径指针**而非反复粘贴大段上下文，防主上下文滚雪球与 `HEAD~1` 漏提交。
