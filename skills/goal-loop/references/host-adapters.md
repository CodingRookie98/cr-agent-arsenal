# 宿主执行后端适配规程 (Host Execution Adapters)

## 概述

P3 的 TDD 执行可以落在多种后端上。本规程定义**后端无关的能力契约**与**降级规则**，避免把技能绑死在某一厂商 CLI 或某个执行模型上。

`goal-loop` 只要求"能派发一个上下文隔离的执行单元并取回结构化结果"；由哪个后端提供，由宿主能力与用户选择共同决定。

---

## 1. 开工前：向用户确认后端 (Ask the User)

进入 P3 前，主调度智能体必须先向用户确认执行后端，再开始派发。使用宿主的用户提问工具（如 `ask_user_question`）给出选项，并按当前宿主的检测结果裁剪：

| 选项 | 适用场景 | 说明 |
|---|---|---|
| **宿主原生子智能体** | 宿主具备子智能体/任务派发原语 | 上下文隔离最佳；优先推荐 |
| **`agy` 无头进程** | 已安装 Antigravity CLI 且用户指定 | 通过 `agy-delegation-workflow` 的 `scripts/dispatch-agy.sh` 派发 |
| **当前会话内联** | 任务小、无需隔离，或前两者不可用 | 最省开销；长任务下需自行控制上下文 |

**默认行为**：本机检测到几个可用后端就列几个选项，不预先假定某一个；**不得**在规程里写死品牌模型名，执行模型以所选后端/CLI 自身配置为准，除非用户显式指定。

---

## 2. 后端能力矩阵 (Capability Matrix)

| 能力维度 | 宿主原生子智能体 | `agy` 无头进程 | 当前会话内联 |
|---|---|---|---|
| 上下文隔离 | 强（独立会话） | 强（独立进程） | 无 |
| 结构化结果回传 | 依赖宿主，通常可回传最终消息 | 依赖 CLI 输出，需落盘约定 | 无（同上下文） |
| 并行派发 | 视宿主而定 | 可并行后台批次 | 串行 |
| 失败可见性 | 中 | 中（需读日志） | 高（直接可见） |
| 适用任务粒度 | 中~大 | 中~大 | 小（约 2 分钟以内） |
| 主要风险 | 宿主差异 | 代理 / OAuth / 环境脆弱 | 上下文膨胀 |

> 无论选哪种后端，**输入规约**统一使用 [atomic-task-template.md](../templates/atomic-task-template.md)，**输出契约**统一使用其第 8 节；后端只改变派发方式，不改变契约。

---

## 3. 宿主能力映射 (Capability Mapping)

把规程中的能力名翻译为当前宿主的实际工具。下表是常见对应关系，用于定位，不是硬绑定：

| 能力 | 典型对应 |
|---|---|
| 代码库检索 | `glob` / `grep`（Antigravity 中为 `find_by_name` / `grep_search`） |
| 网页抓取 | `web_fetch`（Antigravity 中为 `read_url_content`） |
| 子智能体派发 | 宿主原生 subagent / invoke 原语 |
| 目标状态持久化 | 宿主原生 goal 原语（如 `create_goal` / `get_goal` / `update_goal`） |
| 交互式提问 | 宿主的用户提问工具（如 `ask_user_question`） |

**规则**：以当前会话实际声明的工具为准；表中未列出的宿主，按能力语义选择等价工具。

---

## 4. 降级与失败处理 (Degradation)

1. 用户选择的后端不可用（命令缺失、鉴权失败、宿主无原语）时，**立即向用户说明并切换到可行后端**，不静默替换；
2. `agy` 相关故障（代理污染、OAuth EOF、WSL 网络）按 `agy-delegation-workflow` 的诊断规程处理；
3. 内联执行导致上下文接近上限时，先落盘检查点，再切换为隔离后端重启该子任务；
4. 后端切换必须写入计划检查点，保证断点可恢复。

---

## 5. 派发预算与等待纪律 (Dispatch Budget & Waiting Discipline)

> **预算单位是"轮次 / 检查点周期"，不是人类日历时间。** 本规程不引入工期、人日与交期估算——AI 侧的计量单位是**计次**（派发次数、轮次、迭代上限、上下文重置点），因为 AI 的执行时长不可预测且不对承诺有意义，可收敛的只有轮次。

### 5.1 派发即登记 (Register Before Dispatch)
主调度在派发任何子智能体之前，必须在 **`.goal-loop/dispatch-ledger.md`** 维护**派发账本明细**（高频易变数据，遵循 [context-engineering.md](context-engineering.md) §2.1 的落点纪律），并在**计划检查点锚点保留一行派生摘要**（当前在途派发句柄 + 恢复锚点）。账本明细至少包含：

| 字段 | 说明 |
|---|---|
| 派发时间 | 可辨识的时间戳或轮次序号 |
| 角色 | `R1 红队` / `R2 元审判` / `执行子任务 <id>` |
| **派发次数** | 同一角色对**同一基线**的累计派发次数（含超期中断的重派），用于重派上限判定 |
| 后端与句柄 | 后端类型 + 子智能体 id / 进程句柄 |
| 基线 | 被审查或被执行的提交 SHA |
| 状态 | `等待中 → 已返回 / 已超期中断 / 已替代` |

**依据**：未落盘的"我已派发、正在等"在上下文重置或会话重启后即不存在（见 [context-engineering.md](context-engineering.md) 的持久化优先公理），断点恢复将无从判别该重派还是该续等。

**落点分工**：账本明细属高频易变状态，置于 `.goal-loop/`（已被 `.gitignore` 忽略）；计划检查点只保留**派生摘要**（当前在途句柄与恢复锚点），与"计划正文只做阶段批次同步"的纪律一致（[context-engineering.md](context-engineering.md) §2.1）。会话重启后账本明细可能丢失，此时以**计划摘要**为恢复锚点。

### 5.2 提示词自包含约束 (Self-Contained Prompt)
派发给子智能体的提示词**必须自包含其运行所需的全部决策与约束**，严禁把"运行时向人类提问"作为任务的一部分。

**依据（实测约束）**：子智能体在另一智能体存活期间调用人类交互通道会被宿主拒绝（`human interaction is unavailable while the calling agent is owned by another live agent`），导致该子智能体挂死并阻塞整条流水线。凡需要人类裁决的点，必须在派发时给定，或按提问收敛律转为显式默认假设。

### 5.3 等待预算 (Waiting Budget)
1. **同步派发**：调用即在本次返回结果；主调度在当前回合等待，**严禁在等待期间另行派发下一轮审查**（级联顺序铁律见 [dual-round-review](../../dual-round-review/SKILL.md)）。**若该后端无法在调用内取回结果**（调用不返回、或返回时无结构化结果），视为该后端不支持同步模式，必须改用异步派发或宿主可中断的等价原语后方可继续；严禁把“阻塞在调用内”当作等待。
2. **异步派发**：先返回句柄；主调度结束当前回合，以唤醒消息作为返回信号；
3. **预算上限**：一次（**1 个检查点周期**）。**定义**：检查点周期 = 自派发动作发生起，至主调度在计划中**推进到下一个计划检查点**为止的间隔；该周期内主调度不得为空等而停滞。
4. **超期事件的触发条件**（须先可观测，再谈收口）：**主调度主动探测 N 次（默认 2 次）均无新输出，且句柄仍存活**，或句柄已死亡，任一成立即判定为**超期事件**，按 5.4 收口。
   > 该条件是专为**非确定性挂死**（句柄存活但长期无输出）设计的可观测信号：仅靠“超时未返回”无法判别此类故障，而它正是实践中真实发生过的形态。

### 5.4 超期收口与替代路径 (Timeout Closure & Fallback)
超期事件按固定顺序收口，每步都落盘：

1. **中断**：请求中断该子智能体（`interrupt_agent` 或后端等价能力）；
2. **记录**：把中断原因写入 `.review-context/review-<baseline-sha>.md` 或计划 Context Log；
3. **替代**：仅可在下列**隔离合规**路径中选择，并显式声明所选路径——
   - **(a) 原后端重派且收窄范围**（受本条第 5 项重派上限约束）；
   - **(b) 切换至隔离后端**（如 `agy` 无头进程，或宿主等价的可中断隔离原语）；
   - **(c) 若无法保证上下文隔离，审查类派发不得内联降级——必须升级人类裁决**，并在计划 Context Log 记录升级原因。
   > 依据：审查的独立性依赖上下文隔离（见 [dual-round-review](../../dual-round-review/SKILL.md) 铁律 1 与红线）。在主会话内联自审等于由改动作者自审，**不构成任何一轮审查**；因此内联核证**不是**合法的审查替代路径。
4. **恢复**：替代动作完成后，更新派发账本状态与派发次数再继续。
5. **重派上限（B2 的配套封顶）**：同一角色对**同一基线**的重派上限为 **2 次**；每一次超期中断**计入 1 次派发尝试**，且**计入** [dual-round-review](../../dual-round-review/SKILL.md) 铁律 6 的“连续 3 次双轮循环”计数。达到上限仍无产出时，**停止重派**并按 [failure-recovery-protocol.md](failure-recovery-protocol.md) 升级人类裁决。
   > 缺少本条时，“派发 → 超期 → 中断 → 重派”每一笔单独看都合规，却可无限循环：**故障模式会从“挂死阻塞”变成“合规空转”**。

> **边界声明**：中断并如实记录**不违反**"真实产出纪律"（该纪律禁止的是在真实报告返回前**虚构结论**，不禁止对无产出子智能体中断收口）。**用空报告冒充审查结论，才是被禁止的行为。**

## 6. 多智能体并行编排 (Parallel Orchestration)

### 6.1 可并行 / 不可并行 (Parallel vs Serial)
| 场景 | 规则 |
|---|---|
| 同文件写入任务 | **严禁并行**，必须合并为单任务顺序执行，否则产生冲突竞态 |
| 无文件冲突的独立写任务 | 批内可并行 |
| 全局构建 / 全量测试 | **严禁并行**，由主调度在整批结束时统一执行一次 |
| 只读探查型子智能体 | 可并行（不影响工作区） |
| 级联审查（R1 → R2） | **严禁并行**，R2 必须接收 R1 真实报告后方可派发 |

### 6.2 并行预算 (Parallel Budget)
并行作业的规模不以"预计耗时"衡量，而以以下预算约束：

1. **在途派发上限**：同时处于 `等待中` 状态的子智能体数量上限，默认建议 3（超出后新增任务排队），以避免注意力与上下文被稀释；
2. **等待预算**：每个在途派发独立计时（1 个检查点周期），超期各自按 5.4 收口，**单个超期不得冻结整批**；
3. **返回核对**：批次收口时逐条核对派发账本，确认每一条都有终态（已返回 / 已超期中断 / 已替代），严禁存在"被遗忘的在途派发"；
   > **多笔同时超期时，收口动作必须串行逐笔执行**（中断 → 记录 → 替代 → 更新账本为不可并行的原子序列），以避免账本并发互写；单笔等待可与其余在途派发的等待并行；
4. **人类决策预算**：若整批任务依赖人类裁决，该裁决必须在**派发时给定**（见 5.2），不得指望批次运行中途索取。
