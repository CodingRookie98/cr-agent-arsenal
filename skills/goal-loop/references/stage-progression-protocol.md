## 概述 (Overview)

本规程定义了 `goal-loop` 目标实现循环中从阶段 -1（意图对齐）到阶段 5（文档归档）的全生命周期推进法则。
为兼顾**复杂系统的质量确定性**与**局部日常任务的高效敏捷性**，本规程确立**双轨执行通道 (Tiered Execution Tracks)**：

```
                    ┌─────────────────────────┐
                    │ 🎯 目标输入 (Goal Input) │
                    └────────────┬────────────┘
                                 │
                   ┌─────────────┴─────────────┐
                   ▼                           ▼
        【Heavy Track (重型主航道)】   【Fast-Track (敏捷轻量通道)】
        - 适用: 跨模块重构/核心链路/   - 适用: 单文件微调/空状态补全/
                全新复杂业务特性              单函数工具/定向Bug修复
        - 流程: P-1 ➔ P0 ➔ P0.5 ➔      - 流程: 豁免 P-1/P0/P0.5 ➔
                P1 ➔ P2 ➔ P3 ➔                直入 P1(精简计划) ➔
                P3.5 ➔ P4 ➔ P5                P3(Surgical TDD) ➔
                                              P4(定向双轮) ➔ P5
```

---

## 执行通道分级判定矩阵 (Track Triage Matrix)

在启动任务前，主智能体必须首先判定当前任务归属的执行通道：

| 判定维度 | Heavy Track (重型主航道) | Fast-Track (敏捷轻量通道) |
|:---|:---|:---|
| **改动文件跨度** | 涉及 2 个以上文件/模块，或改动公共契约与数据模型，或预期耗时 >10 分钟（与宿主 `AGENTS.md` 判定线一致） | 单文件、局部改动、预期 <10 分钟且不改变公共契约 |
| **契约稳定性** | 涉及底层数据模型、公共 API 签名、全局状态机 | 不改变公共外部契约与数据模型 |
| **未知风险度** | 涉及陌生第三方依赖、分布式竞态或技术选型未决 | 模式成熟已知，无未知第三方依赖 |
| **典型任务范式** | 全新业务系统开发、底层鉴权改造、调度引擎重构 | 补齐界面空状态、增加单一纯函数、调优容限阈值、已知 Defect 精准修复 |
| **阶段裁剪策略** | **强制执行全部阶段 (P-1 至 P5)** | **豁免 P-1, P0, P0.5**，直接从 P1 编写轻量计划并执行 |

> **误判降级**：若 Fast-Track 执行中暴露出跨模块契约影响或未知风险，必须立即重新判定为 Heavy Track 并补做被豁免阶段；判定切换写入计划检查点，不在中途静默升级。

## 阶段 -1: 意图探明与方案对齐 (Ideation & Brainstorming)

* **适用通道**：仅限 **Heavy Track**（Fast-Track 任务直接跳过本阶段）。
* **适用触发条件**：
  - 用户目标较为宏观、存在多种技术选型路径、涉及新业务特性或底层重构。
* **外部技能联动**：**强制激活 `brainstorming` 技能**。
* **核心执行步骤**：
  1. 路径定级：明确界定属于探索型（Spike）、局部改动型（Bounded）还是大型架构型（Architectural）；
  2. 澄清核心诉求：探明真正要解决的业务与技术痛点；
  3. 呈现可行设计：向用户给出 2~3 个具备可操作性的方案对比（权衡优缺点与推荐理由）。
* **门禁准出底线 (<HARD-GATE>)**：
  > **未经用户明确同意（User Nod），严禁擅自动手写代码，严禁进入阶段 1 编写落地计划！**

## 阶段 0: 方案压力测试与技术债评估 (Grilling & Pre-Audit)

* **适用通道**：仅限 **Heavy Track**（Fast-Track 任务直接跳过本阶段）。
* **适用触发条件**：
  - 方案设计涉及并发竞态、分布式状态、安全权限、核心数据流改造或历史遗留代码库。
* **外部技能联动**：**按需激活 `grilling` (`/grill-me`) 技能**。
* **核心执行步骤**：
  1. 方案压力拷问：以红队架构师视角，针对隐式假设、单点故障、性能瓶颈、网络分区与边界回滚方案进行无情拷问；
  2. 未决前沿清空：建立设计决策树（Design Tree），递归追问直至所有盲区决策闭合；
  3. 遗留系统评估（MAY）：若为历史工程，产出现状评估报告（`docs/project/evaluation/evaluation_{title}.md`）。
* **门禁准出底线**：
  > 方案假设 100% 显式化，不存在任何“大概如此”的未决疑点。

## 阶段 0.5: 技术调研与开源选型 (Research & Open-Source Feasibility Spike)

* **适用通道**：仅限 **Heavy Track**（Fast-Track 任务直接跳过本阶段）。
* **适用触发条件**：
  - 引入新第三方库或框架；
  - 实现复杂通用功能（如认证/支付/队列/调度/协议解析/并发控制等）；
  - 涉足陌生技术领域，或技术路径存在未验证假设；
  - 面临“引入开源成熟库 vs 团队自研”的关键架构抉择。
* **豁免条件**：
  - Fast-Track 任务、纯样式/文案调整、已知模式的 Defect 修复、直接复用工程既有模块。
* **外部技能联动**：**派发独立 `research` / `deep-research` 子智能体，按需联动 `find-docs` 技能**。
* **3 级调研工具链 SOP（自上而下逐级展开）**：
  1. **本地代码库检索**：优先查验当前工程内是否已有可复用封装或历史实现（使用宿主的代码库检索能力，如 `glob` / `grep`）；
  2. **GitHub 社区方案评估（优先 `gh` CLI）**：
     - 检索候选库：`gh search repos "<keyword>" --sort=stars`，评估 Star 数、最近更新活跃度与 License 兼容性；
     - 检索实战参考代码：`gh search code "<pattern>"`，学习社区高保真实现范式；
     - 排查已知陷阱：`gh search issues "<topic>"`，排查潜在坑点；
  3. **官方规范与网络检索**：
     - 优先使用 `find-docs` 或 `context7-cli` 获取官方最新 API 签名与破坏性变更信息；
     - 结合 `web_search` 与宿主的网页抓取能力（如 `web_fetch`）查阅 RFC 标准与成熟架构落地实践。
* **上下文工程与隔离执行法则**：
  - **物理隔离**：调研产生大量搜索结果与网页内容，严禁在主调度会话中直接倾倒，必须委派只读子智能体在纯净上下文中运行；
  - **成果落盘**：提炼出高信息密度的《技术调研与开源选型备忘录》，持久化落盘至 `docs/project/research/research_<topic>.md`（参考 [research-spike-template.md](../templates/research-spike-template.md)）。
* **门禁准出底线 (<HARD-GATE>)**：
  > **决策底线：优先复用成熟方案；若决定自研，必须在备忘录中显式阐明现有开源方案不满足的原因；未完成选型裁决前严禁进入阶段 1 编写落地计划！**

## 阶段 1: 计划制定与测试策略裁定 (Planning & Test Scoping)

* **适用通道**：**Heavy Track 与 Fast-Track 均需执行**。
  - **Heavy Track**：完整计划书，涵盖架构图、全生命周期阶段拆解与多维度验收；
  - **Fast-Track**：轻量敏捷计划，聚焦于 1~3 个原子子任务切片、锁定精确变更文件与核心 L0/L1 验收命令。
* **外部技能联动**：**激活 `writing-plans` 技能**。
* **核心执行步骤**：
  1. 编写实施方案：在磁盘创建计划文件 `docs/project/plans/YYYY-MM-DD-<feature>.md`（命名与归档遵循项目既有规范）；
  2. 微型任务切分：严格按照 2~5 分钟/步的标准拆解子任务，每个子任务必须产生自包含、可验证的代码切片；
  3. 制定《测试策略裁定书》：依据 `testing-decision-matrix.md` 对当前改动进行定级（L0~L3），显式记录测试命令与豁免依据；
  4. 固化持久化检查点锚点：在计划头部规范声明当前活跃阶段与检查点。
* **门禁准出底线**：
  > 计划具备完整的任务复选框清单（`- [ ]`），且明确了全流程验收命令。

---

## 阶段 2: 原子子任务拆解与固化 (Task Decomposition)

* **核心执行步骤**：
  1. 将计划中的微型任务固化为独立的任务块（遵循 7 维黄金标准：工作目录、数据契约、依赖规范、测试夹具、架构约束、验收命令、安全红线）；
  2. 技术栈中立，严禁让执行端推测或臆造字段名。
* **门禁准出底线**：
  > 每个子任务提示词具备 100% 自包含性，不依赖前台未声明的隐式上下文。

---

## 阶段 3: TDD 循环实现与原子提交 (Surgical TDD Cycle)

* **外部技能联动**：**开工前按 [host-adapters.md](host-adapters.md) 向用户确认执行后端**（宿主原生子智能体 / `agy` 无头进程 / 当前会话内联），再结合 `agy-delegation-workflow` 派发。
* **环境准备与分支策略**：
  - 基于开发分支（如 `dev`）创建功能分支（如 `feature/goal-<name>`）；
  - **严禁直接在 `main` 或 `master` 分支写代码**。
* **TDD 执行律条 (Red-Green-Refactor)**：
  1. 🔴 **Red**：编写反映期望行为的失败单元测试（L1），运行确认必然失败；
  2. 🟢 **Green**：编写最简代码使测试通过（严禁投机性抽象）；
  3. 🔵 **Refactor**：在测试保护下重构结构、消除坏味道；
  4. ✅ **Verify**：执行本地测试与 L0 静态类型检查，确保 Exit Code 0 全绿；
  5. 💾 **Atomic Commit**：使用 Conventional Commits 提交代码，并立即更新计划中的复选框标记（`- [ ]` ➔ `- [x]`）。
* **测试级别以裁定书为准**：先红后绿的 L1 循环适用于裁定含 L1 的任务；裁定豁免 L1 的改动（如纯配置/依赖升级）按其裁定的级别（如 L0 + L2 + 全局构建）执行，不得据此跳过对应级别验证。
* **门禁准出底线**：
  > 每一个提交均覆盖裁定书要求的测试级别，所有子任务全部标记为 `- [x]`。

---

## 阶段 3.5: 集成验证与跨模块回归 (Integration Verification)

* **适用触发条件**：
  - 所有子任务完成、合并代码前触发；
  - 仅对《测试策略裁定书》中明确包含 **L2 集成测试** 的任务执行（纯 UI 表现层或独立纯工具函数可根据策略裁定书豁免）。
* **核心执行步骤**：
  1. 运行全量集成测试套件（如跨服务接口、数据库装配测试）；
  2. 执行项目全局编译构建（如 `pnpm build` / `cargo build` / `python build.py`），验证类型泛化无断裂。
* **门禁准出底线**：
  > 集成测试零失败，全局构建 Exit Code 0。

## 阶段 4: E2E 验收与双轮对抗终审硬门禁 (Adversarial Gate)

* **适用通道**：
  - **Heavy Track**：全量执行 L3 E2E 验收 + 全量双轮对抗审查；
  - **Fast-Track**：执行 L0/L1 校验 + 针对变更模块的定向单轮红队审查（Diff 边界锁）。仅当改动触及公共契约、核心业务链路、鉴权/并发/数据一致性，或即将合并 PR/发布时，才升级为全量双轮对抗审查；豁免依据必须写入计划的《测试策略裁定书》。
* **核心执行步骤（显式再循环架构）**：
  1. 运行 L3 端到端测试（若裁定书适用）；
  2. **强制激活 `dual-round-review` 技能**：
     - **第一轮 (R1)**：派发独立红队审计子智能体，穿透代码表象，锁定 Diff 边界，核查 Rules of Hooks、SSR 沙盒与极限竞态；
     - **第二轮 (R2)**：派发资深元架构师子智能体，审判第一轮意见，强制拦截历史未改动代码越界挑刺，输出最终裁决明细表；
  3. 🛑 **强制再循环硬门禁 (Delta Re-Loop Hard-Gate)**：
     - 若 R2 裁定 `Blockers > 0`，当前任务状态强制维持进行中；
     - 实施针对性根因修复并原子提交；
     - **严禁擅自判定通过，下一动作必须且只能是将修复提交作为新基线，激活 Delta Re-Loop 重新派发 R1 针对修复证据进行再循环审查**；
     - 循环往复，直至取得独立子智能体给出的 Zero Blockers 裁决；
     - **迭代上限**：同一目标的 Delta Re-Loop 迭代上限为 **5 次**；达到上限仍未清零时按熔断协议升级人类裁决，严禁无上限空转；
  4. 阻断项清零后，将功能分支安全合并回主干/开发分支，并清理临时分支。
* **门禁准出底线 (<HARD-GATE>)**：
  > **必须持有由独立子智能体针对最新提交做出的 Zero Blockers（阻断项清零）终审裁决报告方可合并入库与结项！**

## 阶段 5: 文档全向归档与联动升级 (Documentation Sync)

* **外部规范联动**：对照 `documentation-sync-matrix.md` 逐项复核。
* **未来技能解耦衔接**：本阶段为基础文档闭环层；若项目配置了独立的文档治理技能（Documentation Governance Skill），由主调度器在本阶段末尾无缝派发文档治理工作流。
* **核心执行步骤**：
  1. 架构与接口文档更新（如修改了分层关系、API 签名或数据模型）；
  2. 进度跟踪文档与待办清单闭环更新；
  3. 用户指南与配置手册更新；
  4. 技术决策记录（ADR）归档；
  5. 将实施计划标记为 `[已完成]`，并沉淀最终执行总结。
* **门禁准出底线**：
  > 代码已变而文档脱节的情况彻底清零，目标圆满达成。
