# 改动特征与测试级别判定规程 (Change-to-Test Decision Framework)

## 概述 (Overview)

本规程定义了在 `goal-loop` 目标实现循环中，**什么样的代码改动必须做哪些测试、在哪个阶段执行**的确定性准则。
其核心宗旨是：**精准分层、按需定级、客观取证、拒绝一刀切**。既杜绝微小修改盲目执行沉重耗时的全量 E2E 测试，又防止重大跨模块改动缺乏集成保护导致的回归缺陷。

---

## 1. 测试分级体系 (Testing Hierarchy)

| 级别 | 测试类型 | 运行阶段 | 关注焦点与验证目标 | 执行成本 | 典型工具/命令范例 |
|:---:|---|:---:|---|:---:|---|
| **L0** | **静态代码门禁**<br/>(Static / Lint) | 阶段 3 每次代码变动后 | 语法合法性、静态类型安全、代码异味、未声明依赖排查、死代码清理 | 秒级 (<3s) | `tsc --noEmit`, `eslint`, `cargo check`, `golangci-lint`, `mypy` |
| **L1** | **单元测试**<br/>(Unit Test) | 阶段 3 单任务 TDD 循环内 | 纯函数、算法逻辑、边界分支、状态机流转、无真实外部 I/O 依赖 | 极快 (<10s) | `vitest run <path>`, `pytest <path>`, `go test -run`, `cargo test --lib` |
| **L2** | **模块集成测试**<br/>(Integration) | 阶段 3.5 集成验证阶段 | 模块间接口契约、数据库/存储交互、中间件装配、跨组件状态联动 | 中等 (10s~1m) | `vitest run integration/`, `cargo test --test integration`, `python build.py --action test --test-label integration` |
| **L3** | **端到端测试**<br/>(E2E / System) | 阶段 4 终审验收前 | 用户主干交互链路、CLI 命令全流程、跨子系统集成、真实产物运行验证 | 较高 (1m~5m) | `playwright test`, `run_e2e.py`, 全流程 CLI 批处理验证 |
| **L-Doc** | **文档/元数据检查** | 阶段 5 归档阶段 | 链接有效性、拼写检查、Markdown 语法规范、图表语法合法性 | 极快 (<2s) | `markdownlint`, link-checker |

## 2. 改动特征与测试级别映射矩阵 (Decision Matrix)

在阶段 1 规划与阶段 2 拆解中，智能体必须对照下表确定当前改动必须执行的测试组合：

| 改动特征分类 | 适用典型场景 | 强制执行测试组合 | 豁免条件与说明 |
|---|---|:---:|---|
| **纯工具函数 / 算法模块** | 密码散列、数学计算、时间格式化、数据清洗、正则表达式解析 | **L0 + L1** | **豁免 L2 & L3**。纯内部算法无跨模块副作用，单元测试覆盖核心分支即可保证正确性。 |
| **独立 UI 组件 / 纯表现层** | 按钮、徽章、展示卡片、CSS 样式微调、设计 Token 替换 | **L0 + L1**<br/>(组件单测/快照) | **豁免 L2**；若不直接破坏用户主干流转，可**豁免 L3**。重点检查属性渲染与客户端指令。 |
| **修改公共接口 / 核心领域契约** | `types/` 字段增删改、Go Struct 定义调整、核心领域模型重构 | **L0 + L1 + L2 + 全局构建** | **严禁豁免 L2**！必须运行受影响的所有下游消费者模块集成测试及项目全局编译（如 `pnpm build` / `cargo build`）。 |
| **新增/调整业务 API 端点** | 新增 `/api/v1/orders`、修改订单结算 Service、增加路由处理函数 | **L0 + L1 + L2**<br/>(按需 **L3**) | 必须覆盖 Controller 单元测试与 Service-DB 集成测试；若关联核心用户链路需补跑 E2E。 |
| **核心业务全流程 / 用户链路变更** | 注册登录流程、结账支付链路、跨服务事务、AI 对话生成全生命周期 | **L0 + L1 + L2 + L3** | **全量测试必跑**！任何一级测试失败均构成交付阻断项，必须修复。 |
| **性能重构 / 内部优化 (无行为变更)** | 算法复杂度优化（$O(n^2) \to O(n)$）、引入本地缓存、内存分配调优 | **L0 + L1 + L2** | 依赖既有回归测试（Regression Tests）。无需新增 L3，但需保证既有测试通过且耗时可控。 |
| **构建脚本 / 依赖升级 / 配置变更** | 更新 `package.json` 依赖、修改 `tsconfig`、调整 CI/CD 流程 | **L0 + L2 + 全局构建** | 豁免 L1 编写，重点验证编译打包、依赖解析与下游集成构建。 |
| **纯文档 / 注释变更** | 更新 `README.md`、修改 API 注释说明、规范文档修订 | **L-Doc** | **豁免 L1, L2, L3**。无需运行代码测试套件。 |

## 3. 智能体自主裁定测试范围 SOP (Autonomous Test Scoping)

对于未被上述矩阵直接覆盖的复合改动场景，智能体在**阶段 1（计划制定）**必须执行以下 4 步结构化推理：

### 第 1 步：改动影响面分析 (Blast Radius Analysis)
* 提取待改动或待新增文件的依赖树拓扑。
* **叶子节点判定**：若该文件仅被自身单测引用，影响面评定为 `LOW`；
* **骨干节点判定**：若该文件被 3 个以上上层模块或公共入口直接导入，影响面评定为 `HIGH`，自动触发 L2 强制集成验证。

### 第 2 步：I/O 边界穿透判定 (Boundary Inquiry)
* 该模块在运行时是否执行真实网络请求、文件系统持久读写、子进程拉起或系统环境变量修改？
  - **否（纯内存逻辑）** ➔ 锁定在 **L1 单元测试** 范围；
  - **是（跨边界交互）** ➔ 必须升级为 **L2 模块集成测试**。
  - **⚠️ 防逃逸红线（Mock 边界判定）**：使用 Mock 隔离网络/数据库/外部依赖的业务模块在契约上依然属于跨边界模块，**绝不允许因内部使用了 Mock 而伪称为“纯内存逻辑”以豁免 L2 集成测试**。凡涉及外部协议与跨层装配的关键路径，必须保留至少一组真实装配或真实契约协议的 L2 集成测试。

### 第 3 步：用户链路感知性检查 (User-Facing Check)
* 最终用户、外部系统 API 消费者或 CLI 操作者能否直接观测到该行为或响应格式的变化？
  - **是** ➔ 纳入 **L3 E2E 验收清单**；
  - **否** ➔ 明确记录豁免理由。

### 第 4 步：生成《测试策略裁定书》
在生成的 `IMPLEMENTATION_PLAN.md` 头部，必须显式声明如下裁定小节：

```markdown
## 测试策略与级别裁定 (Test Scope Determination)
- **改动风险定级**: [LOW / MEDIUM / HIGH]
- **强制执行级别**: [如: L0 静态门禁 + L1 单元测试 + L2 集成测试]
- **豁免测试级别**: [如: 豁免 L3 E2E 测试]
- **豁免充分理由**: [如: 本任务为纯内部状态机重构，未改变外部 API 交互契约与 UI 表现]
- **精确验证命令清单**:
  1. L0: `npx tsc --noEmit && npx eslint src/module/`
  2. L1: `npx vitest run tests/unit/module.test.ts`
  3. L2: `npx vitest run tests/integration/`
```

## 4. 阶段与执行时机契约 (Execution Phase Mapping)

1. **阶段 3（子任务 TDD 实现）**：
   - 编码期间：持续运行 **L0**（语法类型检查）；
   - TDD 循环内：运行当前任务指定的 **L1 单元测试**（先红后绿，Exit Code 0 方可 Commit）。
2. **阶段 3.5（集成验证）**：
   - 所有子任务提交完毕后触发；
   - 运行裁定书规定的 **L2 集成测试** 与全局编译构建。
3. **阶段 4（完成验收与双轮终审）**：
   - 运行裁定书规定的 **L3 E2E 测试**；
   - 启动 `dual-round-review`，终审报告中审查者必须核对实际执行的测试覆盖率与真实退出码。
