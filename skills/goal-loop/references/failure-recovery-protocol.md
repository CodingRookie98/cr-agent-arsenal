# 异常恢复与 3-Tries 熔断协议 (Failure Recovery & Escalation Protocol)

## 概述 (Overview)

在大语言模型自动化执行长程任务时，最致命的失控模式是**盲目试错死循环 (Infinite Retry Hell)**：对同一错误反复进行无意义的微调，不仅消耗 Token，还会破坏代码库既有的良好架构。
本协议严格规范了在 TDD 循环、集成测试与终审阶段发生异常时的**分级自愈、自动回退与人类升级仲裁机制**。

---

## 1. 3-Tries 熔断与证据门控重入 (The 3-Tries Rule & Gated Re-Entry)

针对任何单一错误、测试失败或编译异常，智能体连续自主尝试修复的上限严格限制为 **3 次**。
特别地，为防止陷入“盲目试错-自圆其说”陷阱，确立**第 2 次失败后前置微观调研**法则；第 3 次失败即熔断——熔断之后能否继续，由**证据**而非次数决定。

> **上限优先级**：场景级子上限（如编译/静态失败 2 次、重构破坏既有测试 2 次、循环摆动 1 次判定）优先于总上限 3 次生效——先到者先触发其对应动作（编译 2 次转环境/依赖排查，重构 2 次则放弃抽象、保留可用基线），两者不冲突。

熔断之后本协议是一个**四态状态机**，而非一次性升级动作：

```
CLOSED ──第 3 次失败──> OPEN ──Gate 全通过──> HALF-OPEN ──成功──> CLOSED（新周期）
                         │                       │
                         └─ Gate 任一不成立 ──────┴─ 失败或触顶 ──> ESCALATED
```

### 1.1 CLOSED（正常修复）

```
第 1 次失败 ➔ 针对断言与语法精准修复
第 2 次失败 ➔ 强制暂停盲改！触发【微观定向调研】(Micro Research)
              ├── 1. 抓取精准报错堆栈/编译器核心关键词
              ├── 2. 使用 gh search issues 排查依赖库已知 Bug/Issue
              ├── 3. 使用 web_search / find-docs 检索官方已知 Workaround 与变更
              └── 4. 基于第一手权威证据制定第 3 次修复方案
第 3 次失败 ➔ 进入 OPEN
```

### 1.2 OPEN（冻结与取证：STOP → RECORD → RESEARCH → 分诊）

1. **STOP 冻结**：立即停止一切写入型工具调用，避免制造次生破坏；用 `git stash push -m "3-tries-frozen"`（或等价原语）隔离实验性改动，恢复最后一个 Green 基线。
2. **RECORD 记录**：将已尝试方案、失败堆栈与失败机理完整写盘沉淀，生成《自动化熔断报告》（模板见 §4）。
3. **RESEARCH 取证**：汇总微观调研与全代码库排查的权威事实依据——这是 G2 的证据来源。
4. **分诊（ESCALATE 前的闸门）**：
   - **Fast Path / Maintenance-Patch → 直接 ESCALATED（无重入权）**。
   - **Heavy Track → 执行 §1.3 的 Re-Entry Gate 判定**。

### 1.3 Re-Entry Gate（重入准入：四条判据必须全真）

| 判据 | 要求 | 判定方式 |
|---|---|---|
| **G1 新假设** | 提出已失败假设集合 H1..Hn **之外**的根因假设 Hn+1，并写出**判别预测**（「若 Hn+1 成立，则应观测到 X」） | 预测的必须是此前**未观测到**的可观测量及其具体取值 |
| **G2 新证据** | 为 Hn+1 取得**外部新信息**：上游 issue / CHANGELOG / 官方文档 / 社区报告 / 一次新的最小可复现实验 | 该证据必须在上一轮 OPEN 时**不存在于上下文中**；重读既有上下文不算 |
| **G3 非措辞改写** | Hn+1 与任一已失败假设的**判别预测不同** | 判别预测相同即视为同一假设 → 按 §2「循环摆动 (Flapping Bug)」判定，**立即 ESCALATED** |
| **G4 预算未耗尽** | 重入计数 < 2 且单阻塞点成本 < 上限 | 上限 = `min(任务总预算 × 25%, 任务剩余预算 ÷ 3)`；token 与 wall-clock **取先触顶者** |

**默认值是不重入**：任一条不成立即 **ESCALATED**，不得以「再试一次看看」为由放宽。举证责任在申请重入的一方。

**判定示例（校准用）**：

- **放行**：H1「类型不匹配」→ H2「配置项改名」→ H3「缓存未失效」连败进入 OPEN。申请 R1：H4「上游 v3 改了默认序列化格式」，判别预测「应能在上游 CHANGELOG 找到 breaking change 条目」→ 抓到条目 URL ⇒ G1✓ G2✓ G3✓ G4✓ → 放行 2 次尝试。
- **G2 ✗**：「我再仔细读一遍代码，感觉还是 H1 的变体」——无新增外部证据 ⇒ 直接升级。
- **G3 ✗**：H5「是竞态条件」与 H3「缓存未失效」判别预测同为「偶发失败」⇒ 视为同一假设，判 Flapping，直接升级。
- **G4 ✗**：该阻塞点已消耗任务总预算 30% ⇒ 触顶，直接升级，无论当前假设多 promising。

### 1.4 HALF-OPEN（有限探针）

- 只放行**有限**尝试：每次重入最多 **2 次**修复尝试（**不是** 3 次）。
- 重入上限 **2 轮**：总尝试上限 = 3 + 2 + 2 = **7 次**。
- 任一次失败 → **立即回到 OPEN**，不追加尝试；若再次通过 Gate，才允许第 2 轮重入（同样 ≤2 次）。
- 成功 → 回到 CLOSED，重入计数归零。
- **计数落盘**：计划检查点字段 `当前子任务重试计数` 追加重入段，记作 `0/3+R1-1/2`（R=轮次，其后为该轮已用次数）；无重入时省略 `+` 段。该记法不含空白与 shell 元字符，可由 `goal-state-tracker.sh retry` 整值写入。
- **报告同步**：每轮 HALF-OPEN 结束（无论成败）立即更新**同一份**《熔断报告》的重入历史与成本快照——G4 的计数与成本判定以该落盘记录为准，跨会话恢复亦据此判定，不依赖会话记忆。

### 1.5 ESCALATED（人类裁决，非阻塞）

1. **落盘**：报告写入约定路径，作为本次阻塞的唯一交付凭据。
2. **标记**：阻塞点置 `parked`，其依赖项置 `blocked-by: <blocked-item-id>`。
3. **继续**：主调度**继续推进不依赖该阻塞点的独立工作项**——ESCALATED 不等于全流程停摆。
4. **预告**：第 1 次重入通过 Gate 时即发一条异步告知（不等最终升级）：`[Stuck] <阻塞点> 已熔断，正在取证重入；其余 N 项继续推进`。
5. **重开**：人类裁决明确要求继续后，进入新的 CLOSED 周期；该周期预算由人类指令给定（缺省 3 次），**不受本协议重入计数约束**——责任已转移给人。

> **不变式**：全局提示词的 3-Tries 是所有任务的地板，本节只对 Heavy Track **追加**重入权，不放宽任何任务的前 3 次上限；Delta Re-Loop ≤ 5 为独立计数，但同一根因在两处同时触顶时，成本按两者之和计入 G4。

## 2. TDD 阶段异常自愈与回退矩阵 (Unit TDD Failures)

在阶段 3 的 TDD 循环中，按照以下策略进行自愈与回退：

| 失败场景 | 探测机制 | 重试上限 | 回退与自愈策略 | 升级条件 |
|---|---|:---:|---|---|
| **单元测试失败 (Red)** | 编写的代码未能使测试全绿（Exit Code != 0） | 3 次 | 检查断言与输入契约，编写最简实现；若 3 次未果，使用安全暂存隔离改动并回退至该任务开始前的基线。 | 连续 3 次修改无法使测试通过。 |
| **编译/静态类型失败** | 编译器、TypeScript 或 linter 报错 | 2 次 | 检查类型导入、拼写、接口字段是否与模型对齐；必要时恢复至可编译状态。 | 2 次尝试未解决，检查是否存在依赖损坏。 |
| **重构后破坏既有测试** | 🔵 重构步骤中测试变红 | 2 次 | **严禁执行破坏性 `git checkout .`！** 应使用安全暂存 `git stash push -m "failed-refactor"` 隔离实验性重构代码，恢复原 Green 状态基线，禁止为追求抽象而破坏可用性。 | 无法在保持测试全绿的前提下完成重构，跳过重构步骤。 |
| **循环摆动 (Flapping Bug)** | 智能体来回撤销与重做相同的两套逻辑 | 1 次判定 | 立即终止摆动，识别底层架构矛盾。 | 出现一次来回修改立刻停止并记录。 |

## 3. 集成与构建异常处理矩阵 (Integration Failures)

在阶段 3.5 的集成验证阶段，按照以下策略处理跨模块缺陷：

| 异常现象 | 根因诊断方向 | 恢复策略 | 升级条件 |
|---|---|---|---|
| **单个集成测试用例失败** | 局部接口入参/出参格式微调导致契约不匹配 | 定位到具体交互双方模块，回到阶段 3 补充针对性单元测试后精准修复。 | 修复尝试超过 3 次。 |
| **多模块大面积失败 (>3个用例)** | 底层核心模型、全局配置或数据库迁移破坏了上下游契约 | **立即回退代码到集成前状态**，重新评估阶段 1 的规划与接口设计。 | 失败用例数 > 5 个时立即强制熔断。 |
| **环境/工具链依赖失效** | 缺少系统依赖（如 CUDA、本地数据库、Native 动态链接库）或网络代理污染 | **严禁修改业务代码！** 仅排查系统环境配置或依赖安装。 | 属于不可自愈的宿主硬件/网络缺失。 |
| **执行死锁 / 运行超时** | 跨线程/协程竞争死锁，或测试框架进入无限轮询 | 执行时间超过基线 2 倍时直接 Kill 进程，分析并发锁依赖顺序。 | 单次超时超过 10 分钟。 |

## 4. 结构化熔断报告标准模板 (Escalation Template)

当触发 3-Tries 熔断时，智能体必须停止调用写入工具，向用户输出清晰、客观的《自动化熔断报告》：

```markdown
## ⚠️ goal-loop 自动化熔断报告 (3-Tries Escalation)

- **受阻任务**: [子任务名称，如：Task 3 - 结算计算引擎实现]
- **受阻文件**: `[模块主文件路径与单测文件路径]`
- **触发阶段**: [阶段 3 TDD 单元测试 / 阶段 3.5 集成测试 / 阶段 4 终审]
- **已尝试修复次数**: 3 次
- **核心报错信息**:
  ```text
  [此处贴出精准、未经截断的核心编译器或测试框架报错堆栈]
  ```
- **已尝试排查路径与失败机理**:
  1. **尝试 A**: [描述尝试的代码逻辑变动]，结果: [依然报 X 错误，原因是 Y]
  2. **尝试 B**: [描述尝试的修改]，结果: [导致出现新的 Z 错误]
  3. **尝试 C**: [基于微观调研所做的修复]，结果: [未能完全通过，具体瓶颈]
- **微观调研证据链 (Micro Research Evidence)**:
  - **GitHub Issue 检索 (`gh`)**: [是否有类似社区 Issue、缺陷记录或已知 Bug 链接]
  - **官方文档/Web 检索 (`web_search` / `find-docs`)**: [官方对该错误或 API 行为的真实定义与 Workaround]
- **闸门判定记录 (Gate Verdict)**: G1 ✓ / G2 ✓ / G3 ✓ / G4 ✓ → 进入 R1
  （任一条不成立则写：G2 ✗ —— 无新增外部证据 ⇒ 直接升级，不重入）
- **重入历史 (Re-Entry History)**: [无重入则写「无（首次熔断即升级）」]

  | 轮次 | 假设 Hn | 判别预测 | 新证据来源 | 尝试 | 结果 |
  |---:|---|---|---|---:|---|
  | R1 | H2: [根因假设] | [若成立则应观测到 X] | [url / 命令输出] | 2 | [失败: …] |

- **成本快照 (Cost Snapshot)**: 单阻塞点已耗 [tokens / wall-clock]，占任务总预算 [x%]（上限 `min(25%, 剩余÷3)`）
- **第一性原理深度诊断**:
  [分析为什么当前实现无法收敛，是否存在需求定义冲突、上游接口缺陷或环境限制]
- **建议解决方案选项 (提供 2~3 个可行路径)**:
  - **选项 1 (推荐)**: [方案 1 描述，说明改动成本与预期效果]
  - **选项 2**: [方案 2 描述，说明优缺点]
- **请求裁决**: 请人类工程师评估以上选项并下达明确决策指令。
```
