## 1. 元审判概述 (Meta-Challenges on Round 1)

### 1.1 R1 攻击可信度整体评估：**高度中肯，但「修复后是否真解」不在其裁判范围内**

但 R1 的裁判权止于「缺陷存在」，不覆盖「修复是否真解」。**本轮把 4×P1 的现状重判为：1 条真解闭合、2 条半闭合、1 条降级**，同时把 R1 列为 P2 的 **2 条升格为 P1**——因为这两条与已修的两条属**同一失效机理**（缺历史即当无变化 / 门禁看不见自己声明的场景），R1 对它们的分级内部不自洽。

## 3. 次生破坏评估 (Delta Re-Loop & Secondary Regression)

> 本节按派发任务的四个指定问点作答，每点给实跑证据与明确裁决；末尾补两条派发单未点名、但同属次生的发现。

### 3.1 覆盖率下限 0.5 是否会让新仓库/小仓库在 require 下无法起步？——**是，且是双重悬崖；应「可配 + 渐进」**

**实测三组事实**：
1. **本仓自身**：`--truth=require` → `REJECTED（声明覆盖率 6.5% < 下限 50.0%）`。即：**本交付在自身仓库上永远无法通过 require**。`plan:33` 把它记成「符合设计」，但没有任何一份规范性文档告诉读者「require 在迁移期不可用」——`GOVERNANCE.md:96`、`SKILL.md:142`、`change-impact-matrix.md:30` 都只写了判定顺序，未写**前置可达性**。
2. **小仓库构造**：11 篇文档、1 篇声明 → 覆盖 9.1% < 50% → require 恒拒绝，哪怕那唯一一篇是 fresh。**覆盖率下限独立于新鲜度**，所以「诚实但尚未补齐覆盖率」的知识库与「全面漂移」的知识库得到**同一个 REJECT**——两种状态无法区分，这是门禁可诊断性的损失。
3. **CI 默认配置**：零锚点 + `fetch-depth: 1` → `check-doc-drift` **rc=2**（R2-1）。即「还没有任何声明」的新仓库，在把门禁接进 CI 的第一天就红，且**红的原因是环境**而非文档。

**裁决**：默认值 0.5 **保留**（它确实抬高了洗绿成本，见 3.5），但必须补三件事，且**全部是文档/3 行以内代码**，不引入状态机：
- `--min-coverage` 已在 CLI 可配（`audit-doc-health.py:702-703`）→ 把「迁移期设为 0 / 或先只用 warn」写成**明文路线**（GOVERNANCE §3 表下口径 + SKILL 模式 2 步 5 + 矩阵行注）；
- require 的三条阻断理由**分别可辨**（已可辨：文案不同）——但应在 `plan` 的 Active Checkpoint 里显式登记「本仓 require 处于 §2 覆盖率阻断，属迁移期预期」，避免下一轮把「require 红」误读为回归；
- R2-1 的「declared==0 时不因浅克隆报错」。

**明确驳回**：把 0.5 改成「随声明数递减的动态下限」「首次启用宽限期」等机制——需要额外状态与时钟，收益不抵复杂度。

### 3.2 `_verified_ts` 按当日末刻是否掩盖「当天改代码但没复核」？——**是，且比同日更宽（+8h）；但这是日粒度下唯一自洽解，不判缺陷，判口径缺失**

**实测边界**（夹具，`GIT_COMMITTER_DATE` 钉死）：

| 场景 | 锚点提交时间 | 判定 | 期望 |
| :--- | :--- | :--- | :--- |
| 复核于 `2026-11-22`（纯日期） | `2026-11-22T22:00Z`（= 本地 **11-23 06:00**） | **fresh / rc=0** | 应可疑（本地已是次日） |
| 同上 | `2026-11-23T08:00Z` | drifted / rc=1 | 正确 |

- **同一 UTC 日内的任何代码改动恒判 fresh**：因为「复核于=某日」在语义上不携带时刻，任何「当天更早/更晚」的推断都是编造。这不是实现缺陷，是**记录粒度的物理上限**。
- **额外的 8 小时**（UTC+8 作者）：`23:59:59 UTC` = 本地次日 07:59:59，所以「本地次日凌晨改代码」也被判 fresh。这是把「当日末刻」解释成 **UTC** 而非本地时区的直接后果；RFC:92 已明写 UTC，属**已声明行为**，但未声明**后果**。
- **本交付的三处自证全部使用纯日期**（`GOVERNANCE.md:9`、`doc-governance-design.md:7`、`plan:9`）——即 R1-1 的修复让自证变绿，靠的正是这个弱形式。这不构成 self-dealing（RFC:75 明确允许省略 commit），但**门禁的最强形式（commit 形式）在自己的自证上一次都没用**，属示范层缺失。

**裁决**：保留实现（改为「同日一律 drifted」会让「今天写完今天提交」永久不可达 fresh，等价于修复前的病）。补两句口径：RFC:92 加「同一 UTC 日内的代码改动不可辨；跨本地日 0–8h 亦不可辨，热文件请用 `commit <sha>` 形式」；模板 `doc-control-header.md:34` 加同一建议。**不新增开关**（如 `--strict-day`）——没有使用者。

### 3.3 `_declares_anchor` 二次读文件是否合理？——**合理，且不应优化；但有一处静默稀释需要记账**

- 位置 `check-doc-drift.py:214-218`，仅在 `_iter_docs`（`:209-210`）对**根级三个入口文档**求值，最多 3 次额外 `read_text`；随后 `analyze` 会再读同一文件。开销上限 3 次小文件读取（本机整脚本 0.10s），**优化它属于过度工程**。
- 语义上它是**必需的**：豁免规则是「根级入口文档仅在**未声明**锚点时不计入分母」（D-05 / RFC:84）。不做这次预读就无法区分「GOVERNANCE 声明了」与「GOVERNANCE 没声明」，而后者正是最容易被利用的覆盖黑洞。
- **可记账的一处**：`_declares_anchor` 在 `OSError` 时返回 `False`（`:217-218`），而 `analyze` 的 `total_docs += 1` 发生在读文件**之前**（`:240-244`）。一个不可读的根级入口文档会「不计入声明」但**计入分母**，静默稀释 `coverage`。方向 fail-safe（压低覆盖率），P3 级，记 Backlog，不本轮修。
- 结论：**保留，不动。**

### 3.4 与既有 BK-0028（PASS/REJECT 单一判定出口）是否真正一致？——**不一致：症状消除，不变量被复制破坏**

- BK-0028 D1-7 的原文落在 `audit-doc-health.py:102-108` 的 docstring：*「此前 PASS 分支与 REJECT 分支各自重算同一批条件，两处漂移即出现『同一份体检结果既满足 PASS 又给出 REJECT 原因』的自相矛盾。现在只在这里判一次。」*
- 修复后的实际结构：`evaluate_verdict`（`:129-137`）与 `main()`（`:844-861`）各持一份**逐字同构**的三段判定（未启用 → 覆盖率 → 分数），仅文案有细微差异（后者少了「（删锚点不能替代修复漂移）」后缀）。
- 因此：**「同一屏出现完美与 REJECT」的可见症状已被消除**（实测通过），但**「两处各自重算」的成因被原样复制**。BK-0028 要求的是**单一出口**，本轮交付的是**两个同源出口**。
- 裁决：判 🟡 P2（无活分支，故不阻断），但**必须在本轮内改为单出口**——因为这是**本轮新增**的同型缺陷，且修复成本为**净减代码**（删掉 `:844-861` 的梯子，改用 `evaluate_verdict` 返回的 `reasons`）。把「新引入的同型缺陷」留给下一轮，等于承认本轮修复没有真正理解 BK-0028。

### 3.5 其它次生破坏（派发单未点名，但同属本修复引入）

1. **`--fail-on-drift` 与覆盖率互相不认**：覆盖率下限只活在 `audit-doc-health`（`:132-137`），而矩阵 DoD 指定的命令是 `check-doc-drift --fail-on-drift`——**门禁的两半各自只守一半场景**：drift 脚本看得见漂移、看不见洗绿；audit 看得见洗绿、在被指定为 DoD 的模式（warn）下不阻断。详见 R1-2 行。
2. **浅克隆期间的真值块仍在「编造数字」**：`audit-doc-health` 在浅克隆中输入出 `drifted 1 / 真值分 0.0`（实测），并把它写进 `truth` 块与 REJECT 理由。即使未来改成 rc=2，**报告产物本身已经撒谎过一次**。建议在 `truth` 块加 `"environment": "shallow"` 之类的最小标记，而不是让分数承担环境语义。
3. **计划/台账的自证措辞已与实测对齐**：`plan:33` 的「3/46、fresh 3、15.0/15、rc=0」与「require → REJECTED（覆盖率 6.5%）」经本轮实测**逐项一致**（这是修复提交最扎实的一部分）；`plan:34` 的「182 passed」亦实测一致。**没有发现新的自证失真**——这一点必须给修复提交记正分。
