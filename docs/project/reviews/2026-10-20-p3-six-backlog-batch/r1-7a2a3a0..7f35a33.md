## 1. 第一性原理与本质溯源分析

本批次不是功能开发，而是**用可机械执行的判据替换三条「看似生效、实则空转」的判据**（GNU BRE 的 `\?` 恒匹配、裸子串幂等判据、零根校验），并把两条口径（GOVERNANCE 豁免边界、作废轮次留痕）写进真相源。因此第一性问题是三问：

1. **读写文法是否同构**：新判据识别的形态，是否覆盖写方实际写出的全部合法形态？
2. **测试是否可被变异杀死**：把被测行为改回旧行为后，新用例是否必红？
3. **宣称是否与取证同宽**：提交信息与计划的数字，能否在纯净树上独立复跑？

### 1.1 三条判据的同构性检验

- **写读同构（幂等判据）**：`manage-doc-index.py:290` 以 `f"- [{title}](./{filename}) — {kind}"` 写入，`filename` 只需通过 `validate_file_arg`（`:126-131` 仅拒绝空串、`/`、`\`、`.`、`..`），**空格与 `)`、`#`、`?` 均为合法输入**；而 `has_doc_link` 的正则 `:262` 为 `\]\(\s*\./([^)\s?#]+)(?:[?#][^)\s]*)?\s*\)`，字符类排除空白与 `)`。读写文法不同构，round-trip 在合法输入上不闭合（实测见 R1-2）。
- **测试同构（变异可杀性）**：用 BASE 版 `check-review-report.py` 跑 HEAD 新增用例，结果 `1 passed`——新用例断言的四个子串在 BASE 文案中全部成立，删除新文案仍绿（R1-4）。BK-0008 的「可定位性」没有被测试固定。

## 2. 运行时与 SSR/沙盒安全推演（条件维度）

**未激活（非客户端/SSR 改动）**。判定依据：本次 diff 只触碰 3 个 Python 脚本（`prepare-review-context.py`、`check-review-report.py`、`manage-doc-index.py`）、4 个测试文件与 4 份 Markdown；无 DOM/模板渲染、无 HTTP handler、无浏览器端代码、无 SSR 数据流、无鉴权/会话/序列化边界，因此 XSS/CSRF/原型污染/SSR 注入面不适用。

仍做了三条「同维度替代」推演，均未构成新缺陷：

- **文本通道注入**：`prepare-review-context.py:210-227` 把 `git status -s` 路径原样写入 Markdown。实测 git 对控制字符路径加双引号并转义（`"文档 名.md"` 输出为 `"\346\226\207..."`），**换行注入不成立**；残余问题是路径不还原（R1-7，可用性而非安全）。
- **ReDoS**：新正则 `[^)\s?#]+`、`(?:[?#][^)\s]*)?`、`\s*\)` 无嵌套量词，回溯线性；实测万级字符输入无放大。
- **命令注入/路径穿越**：`_run_git` 以参数列表调用，未拼 shell；`--archive-root` 仅参与 `os.path.abspath` 与 `makedirs`，无 `shell=True`。**但**根边界可被符号链接绕过（R1-3），属契约面而非注入面。

## 3. 红队攻击路径推演 (Concrete Failure Scenarios)

- **S1 幂等破坏链（R1-2）**：新增归档文档名含空格（如 `ADR 0001 foo.md`，`validate_file_arg` 放行）→ 连续两次 `manage-doc-index.py register` → 第二次不再输出「已登记，跳过」，而是追加重复清单行并把 `**当前版本**` 再升一个补丁号 → 第三次继续 → 实测 `V1.0.4` 与 3 行重复条目。下游 `check-doc-control-sync` 只校版本与修订行是否同步，**不会**发现重复条目；索引从此多源真相。
- **S2 空转门禁链（R1-4）**：把 `check-review-report.py:293-296` 的新文案整体删除或改错 → `test_unclosed_fence_message_identifies_report_and_parity` 仍绿（BASE 文案已满足四个子串）→ 未来重构可无声丢失「报告名 + 围栏数 + 偶偶性」的可定位信息，而归档报告门禁在运行时才报错，回归期无任何提示。
- **S3 宣称污染链（R1-5、R1-8）**：R1 派发时 scaffold 出**未跟踪**的 `docs/project/reviews/2026-10-20-p3-six-backlog-batch/README.md`（空台账）→ `test_existing_archives_all_pass_gate` 扫描磁盘目录 → 全量 pytest 由 499 变 1 failed → 若 R2 在同一工作树复跑，会得到与 R1 相同但**归因错误**的「HEAD 有失败」结论；纯净树复跑才回到 499。
- **S4 路径守卫绕过链（R1-3）**：`ln -s / /tmp/rootlink` → `prepare-review-context.py --archive-root=/tmp/rootlink` → 校验通过（rc=0）→ 归档根落在 `/`，若进程有写权限即把报告写到仓库外任意位置，直接违背 `SKILL.md:118` 的「报告不得散落到仓库外任意位置」。同类：`--archive-root=../..`、`C:\Users\Public\reports` 均通过。
- **S5 数字口径链（R1-5）**：R2 若沿用提交信息的「消除 154」作为批次收益，会与「BASE 94 → HEAD 94」的实测冲突；「消除 154」最可能来自与更早一次 248-failed 运行（`%TEMP%` 中 9 时段的基线日志，非本次取证）的错位比较。该归因本身**未验证**，但「对 7a2a3a0 消除 0」是已验证事实。
- **S6 上下文可用性链（R1-7）**：未跟踪中文/空格文件名 → 注入块输出 `\346\226\207\346\241\243 \345\220\215.md` → R1/R2 拿到的「未跟踪清单」是无法 `open` 的转义串 → 审查者漏看真实新增文件（本仓库当前未跟踪文件以 ASCII 为主，风险为潜在）。
