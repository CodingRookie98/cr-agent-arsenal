## 1. 第一性原理与本质溯源分析

### 1.1 缺陷的三层本质：不是「少了一个 Unicode 码位」，而是「解析失败未被建模」

R1-01 的表层是 ASCII 空白类与 gawk `[[:space:]]` 的语义差；但放行之所以发生，是三层因素叠加：

1. **词法层（lexer）**：原 Bash 用 `[[:space:]]`（UTF-8 locale 下 `iswspace` 认 U+3000/U+2002 等），Python 用 `SPACE = " \t\n\v\f\r"`。同一张表在两套实现里被切成不同的 token 流。
2. **控制流层（parser/consumer）**：`_check_id_alignment` 用 `if not round_r1: continue` 把「抽取结果为空」直接解释为「本基线无缺陷」，于是两向 ID 对齐与「R2 空裁决表禁止放行」同时短路。**空集被当成了合法语义，而不是待诊断的解析状态。**
3. **契约层（grammar）**：「0 个稳定 ID」本身是二义的——既可能是真正的零缺陷报告（表头后无数据行），也可能是解析失败（有数据行但一行都没被契约正则捕获）。修复必须引入第三个信号（行内容）来消歧，否则要么 fail-open，要么误拒干净报告。

因此，R1-01 的根治标准不是「`\s` 改完就结束」，而是「解析失败必须可观测，且不能被当成空表放行」。本次修复正是按这个标准做了两层：词法层改 `\s`/`strip()`；控制流层新增 `_has_unparsed_id_rows()` 守卫。

### 1.2 修复的四点与各自判别力

| 变更 | 位置 | 关闭的行为 | 独立验证 |
|---|---|---|---|
| 表头正则改 `\s` | `check-review-report.py:93` | U+3000/U+2002 夹在表头竖线与「稳定 ID」之间时表头不被识别 | F01/F02 |
| 单元格去边改 `\s` | `check-review-report.py:242-243` | ID 单元格首尾 U+3000/U+2002 导致 `_ID_CELL_RE` 不匹配 | F04（尾随）、F01（首部） |
