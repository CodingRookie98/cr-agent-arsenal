# 第一轮对抗审查报告 (Round 1 Red-Team Review Report)

> 🧠 **From Hindsight memory (dual-round-review 审查报告持久化归档契约)** — `dual-round-review` 技能的交付凭据归档契约规定：审查报告必须全文逐字落盘至版本控制库，并由机械门禁 `check-review-report.sh` 实施 7 项不变式校验（含稳定 ID 双向对齐、`--require-verdict=PASS` 精确匹配与 SHA256 防伪比对），彻底消除会话转录失真与自证假放行。

## 1. 第一性原理与本质溯源分析

- **改动性质定性**: 存在浅层修补（Palliative Patching）嫌疑与次生破坏
  - 本次变更旨在闭环 6 张 P2 backlog 卡片（BK-0003, BK-0004, BK-0020, BK-0033, BK-0034, BK-0040），涵盖 `dual-round-review`、`doc-governance` 和 `spec-evolution` 三个技能的门禁及事实判定脚本。
  - 虽然部分改动直击根本原因（如 BK-0004 对终审裁决唯一性的机械计数、BK-0033 对非 UTF-8 环境输出流的硬化），但在关键防御链路上存在严重的浅层修补问题：
    1. **BK-0040 兜底范围过窄**：仅在 `main()` 中对 `build_findings` 加了 `try...except`，却忽视了后续 `validate_anchor` 和 `render_report` 对 `facts` 畸变字段的二次消费，导致类型逃逸漏洞依然存在。
    2. **BK-0003 表头提取过严**：重构 `section_ids()` 时，误将提取表头硬编码为以 `稳定 ID` 开头，直接与自身技能官方模板 `templates/r2-report.md` 的 `| R1 稳定 ID |` 表头契约产生冲突，引入了导致合法审查归档被误判阻断的次生缺陷。
- **物理与业务一致性**:
  - `check-review-report.sh` 的本质物理契约是保证 R1 与 R2 审查报告的对抗双向对齐，但由于正则表达式割裂了与模板之间的契约一致性，破坏了工具链自洽。
  - `judge.py` 作为确定性门禁判定器，其业务契约是区分“输入格式错误/环境错误（exit 2）”与“存在阻断项（exit 1）”。当前实现使得特定嵌套字段畸变时，解释器依然抛出裸 traceback 并以 1 退出，未能恪守该退出码物理边界。
- **过度设计审计**:
  - BK-0004 严格遵守了 YAGNI 指令（计数 ≤ 3 行，未引入过度复杂的 YAML/Markdown 语义解析器）；
  - `manage-doc-index.py` 在 `find_revision_header` 中引入了章节作用域限定，方向正确，但章节结束判定过于粗暴（任何标题均截断），存在过度防御倾向。

## 3. 红队攻击路径推演 (Concrete Failure Scenarios)

### 攻击路径 1: 官方 R2 模板表头导致合规交付被误杀阻断 (BK-0003 改动次生缺陷)
- **触发条件**:
  R2 审判子智能体严格按照 `skills/dual-round-review/templates/r2-report.md` 模板编写终审裁决书，其第 2 节表格表头为：
  `| R1 稳定 ID | 最终定性 | 复核依据与反证据 | 残余风险 |`
- **复现推演**:
  1. R1 报告登记了 `R1-1` 缺陷并落盘；
  2. R2 报告针对 `R1-1` 给出终审定性，复制官方模板结构落盘；
  3. 执行 `check-review-report.sh <archive_dir>`；
  4. 脚本调用 `section_ids "$f" "## 2. 最终裁决明细表"` 解析 R2 报告；
  5. 内部 awk 脚本执行 `if ($0 ~ /^\|[[:space:]]*稳定 ID/) tbl = 1`；
  6. 由于表头首列为 `R1 稳定 ID`，正则 `^\|[[:space:]]*稳定 ID` 匹配失败，`tbl` 保持为 0，明细行全被跳过；
  7. `round_r2` 提取结果为空，触发第 381 行断言：`错误: 基线 <key> 的 R1 缺陷清单非空，但同基线 R2 裁决明细表为空（禁止空表放行）`；
  8. 脚本退出码为 1，合法合规交付被错误阻断！
  9. **反向漏洞**：若 R1 报告本身为 CLEAN（无缺陷），则 R2 伪造的任何非法 ID 也会因 `R2_IDS` 提取为空而绕过方向一校验（`while read -r id; do ... done <<<"$R2_IDS"`），造成防凭空捏造机制失效！
- **涉及代码**: `skills/dual-round-review/scripts/check-review-report.sh:307`

### 攻击路径 2: 畸形 facts 击穿 judge.py 消费期浅层防御，裸 traceback 伪装阻断项 (BK-0040 未根治)
- **触发条件**:
  外部传入的 `--facts` 输入存在非标准类型（如上游 schema 演化、或者手工构造/截断时发生嵌套字段畸变），且触发了规则锚点校验（如包含 C-06 文件超限）。
- **复现推演**:
  1. `facts["root_prompt"]["headings"]` 被赋予整数 `5`，`facts["skills"][0]["oversized_files"] = ["SKILL.md:1200"]`；
  2. `judge.py` 启动，`load_facts` 仅检查顶层类型（`root_prompt` 是 dict），放行；
  3. 进入 `main()`，`build_findings(facts)` 执行成功，生成含 `RULE_SIZE` 规则锚点的 finding；
  4. 离开 `try...except` 保护区，进入行 400 的锚点校验循环；
  5. 执行到 `validate_anchor(anchor, repo_root, headings)`，匹配 `RULE_ANCHOR_RX`；
  6. 执行行 112：`for heading in headings:`；
  7. 解释器抛出 `TypeError: 'int' object is not iterable`；
  8. 由于该调用位于 `build_findings` 外部，未被兜底捕获，Python 抛出未捕获裸 traceback 并强制以状态码 **1** 退出；
  9. 编排方读取退出码 1，误将“输入格式畸变”当成“代码存在 BLOCKER/HIGH 缺陷”，破坏了门禁退出码契约。
- **涉及代码**: `skills/spec-evolution/scripts/judge.py:385-396`, `judge.py:405`, `judge.py:112`

### 攻击路径 3: 生成报告时消费非字符串 generated_at 导致进程崩溃
- **触发条件**:
  事实文件中 `facts["generated_at"]` 传入 UNIX 时间戳整数（如 `1728900000`），并指定 `--report` 参数。
- **复现推演**:
  1. `build_findings` 顺利通过；
  2. 进入 `if args.report:` 分支，调用 `render_report(facts, findings)`；
  3. 执行行 331：`.replace("{{DATE}}", (facts.get("generated_at") or "")[:10])`；
  4. 对整数切片触发 `TypeError: 'int' object is not subscriptable`；
  5. 进程崩溃并输出裸 traceback，以退出码 1 退出，再次打破退出码契约。
- **涉及代码**: `skills/spec-evolution/scripts/judge.py:331`, `judge.py:417`

### 攻击路径 4: 修订历史章节内包含子标题导致定位截断 (BK-0020 边界脆弱)
- **触发条件**:
  托管索引文档的『修订历史记录』章节中为了补充说明，插入了 Markdown 子标题（例如 `#### 历史维护规则`），其后才是 `| 版本号 | ...` 表格。
- **复现推演**:
  1. `find_revision_header` 扫描到 `### 修订历史记录`，`section_start` 被赋值；
  2. 继续向下扫描到 `#### 历史维护规则`，匹配 `re.match(r"^#{1,6}\s", stripped)`；
  3. 执行 `else: break`，过早跳出循环；
  4. 函数返回 `None`；
  5. 调用方抛出 `IndexMaintenanceError` 拒绝登记，导致文档索引无法自动维护。
- **涉及代码**: `skills/doc-governance/scripts/manage-doc-index.py:183-184`

## 5. 第一轮结论概要

本轮对抗审查对 6 张 P2 backlog 卡片的 12 个文件改动（821 行代码与测试，以及文档规划）进行了第一性原理穿透与故障注入推演。

**关键阻断项结论**:
1. **R1-1 (P1 Blocker)**：`check-review-report.sh` 引入的表头抽取逻辑与官方 `templates/r2-report.md` 模板发生契约冲突，使标准交付流程产生确定性误阻断，属于严重的次生破坏。
2. **R1-2 (P1 Blocker)**：`judge.py` 对 BK-0040 的修复属于“浅层创可贴”，防御范围未覆盖整个消费生命周期，导致特定类型畸变仍能以退出码 1 逃逸并打出裸 traceback。

本轮审查检出 **2 项 P1 阻断项 (Blockers)**、**2 项 P2 优化建议**、**1 项 P3 建议**。
