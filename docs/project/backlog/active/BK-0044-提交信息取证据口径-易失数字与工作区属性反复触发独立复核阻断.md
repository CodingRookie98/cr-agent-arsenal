## 1. 背景与问题陈述
现象：本会话的独立复核循环中，同一根因（提交信息写入未经现场复核的易失数字或不可复核属性）四次触发关注，其中两次被判为阻断项，均以「归档卡追加更正记录 + docs/index.md 升版」收口，未改写已推送历史。根因：提交信息的「取证」行同时承担两类内容 —— 可长期复核的门禁退出码与只有当次成立的一次测量值（耗时、计数、权限），二者未加区分；审查者按「宣称与取证同宽」逐项复测时，一次测量值必然不可复现。影响：每次复核都要消耗一轮修复与更正提交，且更正记录本身又在累积；不涉及功能缺陷（两批代码面均经独立复现通过）。建议：在提交信息模板层面区分「门禁结论」（可复核）与「本机实测」（一次测量、声明不可复现），或把易失数字移出提交信息、改为落盘到临时证据文件；本卡先登记判据，实施范围与落点待裁决。

## 2. 影响面与技术考量
- 涉及模块: 待对齐（实施载体候选：提交信息模板 / 提交前校验脚本 / 文档规范条文；开工时定稿）
- 风险点: 待评估（四条为政策型准则，若最终无机械验证入口，结项只能人工判定 —— 这是本卡的主要风险；另记：本卡 §3 DoD 与 frontmatter 的验收准则由 `manage-backlog.py` 同源写入但**无一致性门禁**，收口时曾因两处文本分歧被判阻断（独立复核 V14 阻断项），两处须逐字同源；`scaffold-doc.sh` 的 backlog 骨架是同类的第二双写入口（frontmatter `acceptance_criteria` :404-407 与 §3 DoD :416-418，默认文案不同）—— 两处的一致性校验可另立小项）

## 3. 验收准则与验证设计 (DoD)
- [ ] 明确提交信息「取证」行的取值口径：只写门禁退出码与「本机实测」范围；若写具体数字（可用命令在同一树复现的用例计数、findings 计数等），必须现场重跑并把命令与原始输出一并落盘留痕
- [ ] 明确一次测量值（耗时等不可由命令复现的浮动量）的写法：必须标注「一次测量」并以区间或多次采样表述；不得以单一精确值表述为常数性事实
- [ ] 明确不可由 git 复核的工作区属性（文件权限等）不得作为完成度宣称
- [ ] 口径成文后，历史提交的更正记录（BK-0039 §5、BK-0042 §5）保持原貌，不回改
