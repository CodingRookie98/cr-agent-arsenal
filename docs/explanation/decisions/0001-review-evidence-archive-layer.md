## 1. 背景与上下文 (Context and Problem Statement)

`dual-round-review` 的两轮提示词模板定义了完整的报告输出契约（R1 的攻击路径推演与缺陷清单、R2 的裁决明细表与放行结论），但**技能全流程没有任何一步要求把子智能体返回的报告原文写入磁盘**：铁律 5 只规定写入 8 字段摘要锚点，且该锚点所在目录被 `.gitignore` 忽略。

**实证缺口**：本仓库 2026-09-21 的审查产物摘要文件自述「全文见会话记录」；该交付唯一进入版本库的审查内容，是实施计划中**手工重写**的摘要表格，指向一个会话结束即失效的子智能体句柄。

**根因**：两类生命周期与可重建性完全不同的产物被塞进了同一个容器 ——

| 维度 | ① 运行时状态 | ② 交付凭据 |
| :--- | :--- | :--- |
| 生命周期 | 一次审查循环（小时级） | 交付审计期（长期） |
| 变更频率 | 高频改写 | 一次写入，只读 |
| **可否重建** | **可** | **不可**（原文只有那一次生成） |
| 社区惯例位置 | 隐藏目录 + `.gitignore` | 版本库（同 ADR） |

把 ② 存进 ① 的容器，结果就是**全文干脆没有落盘这一步**。

**硬性约束**：技能是可分发资产（会被装进第三方项目），归档位置不得硬耦合宿主目录结构；报告必须以**逐字原文**保存（添加任何元数据都会改变内容并使其指纹失去意义）。

---

## 2. 考虑的备选方案 (Considered Options)

* **方案 1**: 保持 `.review-context/`，仅用 `.gitignore` 负向白名单让归档文件被跟踪
* **方案 2 (选定)**: 两层分离 —— 运行时状态留在隐藏目录，交付凭据进入版本库跟踪的 `docs/project/reviews/`，并对该目录实施**治理扫描豁免**
* **方案 3**: 顶层 `reviews/` 独立目录（与 `docs/` 平级）

---

## 3. 最终决策与裁决 (Decision Outcome)

选定 **方案 2**：按「可否重建」切分两层，交付凭据进入 `docs/project/reviews/<YYYY-MM-DD>-<slug>/`（推荐默认，宿主规范优先），并新增三层拓扑中的**机械门禁** `check-review-report.sh`，使「索引齐备 / 报告在位非空 / SHA256 指纹一致 / 两轮区块齐备 / 稳定 ID 对齐」可被机械证明。

### 3.1 积极后果 (Positive Consequences)

* ✅ **凭据可持久化且人类可读**：`git clone` 后即可阅读 R1 攻击路径推演与 R2 裁决明细表，不再依赖会话留存
* ✅ **消除转录失真通道**：R2 输入由「主智能体内联转录」改为「归档文件路径 + SHA256 指纹」，R2 可独立核验原文（本 ADR 的审查过程中该通道已被真实使用并完成指纹校验）
* ✅ **复用既有治理门禁**：归档位于 `docs/` 内，天然被索引体系与健康体检覆盖
* ✅ **误报证据链完整保留**：R2 驳回 R1 的误报时，R1 原文同样归档，去伪存真的推理过程可追溯

### 3.2 消极后果与已知代价 (Negative Consequences / Trade-offs)

* ⚠️ **凭据落入了「会写它、会判它」的治理域**：归档目录位于 `docs/` 下，必须为其建立**扫描豁免**，否则每次真实审查交付都会单调侵蚀知识库健康度（实测：首次归档即把健康度从 100 打到 97.1，外推约 11 次交付跌破 80 分门槛并被硬拒）
* ⚠️ **豁免面必须覆盖全部消费者，而非仅扫描器**：审查中实证发现，治理域内共有四个消费者读取该目录，其中 `trim-revision.py` 是唯一具备**写**能力的 —— 若未豁免，其 `--fix`（该命令由健康体检脚本自身推荐）会就地改写归档报告，破坏逐字红线并使其指纹与台账永久失配
* ⚠️ **指纹的信任边界有限**：SHA256 由转录者本人计算登记，属自证式校验 —— 可检出**事后篡改与整体截断**，**不覆盖转录期的改写、压缩与选择性摘录**；该残差为显式登记的已知取舍，转由 R2 的文件通道承担
* ⚠️ **归档体量无自动保留策略**：登记为待办，待体量成为实际问题后另行立项

## 4. 备选方案详细对比与论证 (Pros and Cons of the Options)

### 4.1 方案 1: `.review-context/` + `.gitignore` 负向白名单

* 概况: 复用社区惯例的隐藏目录，仅用白名单让归档文件被跟踪
* **未采纳理由**: 「忽略整个目录 + 逐文件白名单」的规则脆弱 —— 新增轮次报告若忘记加白名单即静默丢出库外，把**持久化可靠性**建立在一个易漏的人工步骤上；且运行时状态（高频改写）与交付凭据（只读）混居同一目录，语义仍混淆。审查阶段对此的核实结论：社区隐藏目录惯例服务的是**运行时状态与配置**且默认被忽略，不适用于审计凭据

### 4.2 方案 2: 两层分离 + `docs/project/reviews/` + 治理豁免（选定）

* 概况: 运行时状态保持社区惯例的隐藏目录；交付凭据进入版本库，并对归档目录声明治理豁免
* **选定理由**: 受众诉求各自闭合（子智能体可寻址、人类可阅读、编排者可机械核验）；与宿主既有的「`.goal-loop/` 高频态 + `docs/project/plans/` 真相源」分层同构；豁免语义可被集中登记与审计

### 4.3 方案 3: 顶层 `reviews/` 独立目录

* 概况: 与 `docs/` 平级，职责最清晰，不污染知识库象限
* **未采纳理由**: 脱离既有治理工具链 —— 报告将不受断链扫描、健康体检与索引体系覆盖，需另行建立并维护一套治理规则，投入产出比劣于方案 2

## 5. 审查证据与演化记录 (Review Evidence & Evolution)

本决策经**四轮对抗审查**闭环取得 Zero Blockers 放行（完整报告全文见关联审查凭据），其中三条发现直接塑造了最终形态：

1. **放行开关的判定语义**：初版 `--require-verdict=PASS` 以「首行是否包含准予交付四字」判定 → 官方占位符串自身即含该词元，导致「阻断交付」拿到假 PASS 凭据。**演化**：改为字段值精确匹配（剥离前缀与空白后必须恰好等于「准予交付」），并在契约模板中消除占位符歧义
2. **归档产物反噬治理门禁**（本 ADR §3.2 第一条代价的实证来源）：健康度 100 → 97.1，且首次运转即击穿交付自身的验收线
3. **豁免面残缺**（本 ADR §3.2 第二条代价的实证来源）：初版豁免只覆盖两个扫描器，遗漏唯一可写的 `trim-revision.py`（实测可改写凭据至指纹变化）与 `generate-llms-txt.py`（实测机器地图 18 vs 21 条漂移）
