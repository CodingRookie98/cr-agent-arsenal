## 1. 背景与目标 (Problem & Goals)

### 1.1 要解决的问题

大语言模型是 **Next-Token Predictor + RLHF** 的产物。每次设计决策（配色、布局、文案）都倾向选择「最可能取悦大多数人的安全 Token」——结果是千篇一律的 **AI Slop**：紫色渐变、左文右图 Hero、Bento 卡片、居中大标题、无意义的装饰性微交互。

这不是「模型不会设计」，而是**统计均值本身就是平庸**。技能要解决的是：

1. **如何把模型推出分布均值**（Discover）——不能靠「随机一点」这种指令，模型只会预测「听起来随机」的 Token；
2. **如何在没有人类品味的条件下判断好坏**（Define）——需要外部 Critic 与可核验的结构清单；
3. **如何避免加法惯性**（Deliver）——AI 天然倾向堆元素，而品味往往体现为删减。

### 1.2 目标

- 让无设计背景的用户也能得到**不像 AI 生成**的界面产物；
- 把「品味」这个模糊概念拆成**可执行、可核验**的信号，而不是靠模型自评「我觉得这样更好」；
- 与 `frontend-qa-gate` 明确分工：本技能管**好不好看**，它管**能不能用**。

### 1.3 非目标

- 不做可用性/无障碍/性能验收（那是 `frontend-qa-gate` 的职责）；
- 不做设计系统长期治理（Token 库、组件库演进）；
- 不替代人类创意总监——方向选择与最终签收永远归人。

## 2. 理论支柱 (Theoretical Pillars)

### 2.1 黄金公式

```text
World-Class AI Design = 外部随机种子 + 独立 Critic 闭环 + 多模态增强 + 残酷减法
```

四项各自对应一类失效模式：

| 支柱 | 对冲的失效 | 为什么不能省 |
| :--- | :--- | :--- |
| **外部随机种子** | 模型输出收敛到统计均值 | 种子由脚本生成、模型不可预测 ⇒ 真正把输出推出分布 |
| **独立 Critic 闭环** | 自评偏差（模型看不出自己的问题） | 全新上下文 + 只看产物 ⇒ 切断「我知道我为什么这么写」的辩护通道 |
| **多模态增强** | 纯文本无法评估视觉密度/质感 | 有截图才谈视觉；无截图则显式降级，禁止假装看见 |
| **残酷减法** | 加法惯性（越加越像模板） | 删除是唯一能同时提升密度与个性的操作 |

### 2.2 双钻模型映射

```text
D1 Discover（发散）  →  D2 Define（收敛+打磨）  →  D3 Deliver（减法+审计）
   打散均值              注入品味                 剔除 AI 痕迹
```

## 3. 流程拓扑 (Process Topology)

| 阶段 | 目标 | 核心技法 | 产物 |
| :---: | :--- | :--- | :--- |
| **D1 Discover** | 打散统计平庸 | `generate-seed.py` 生成种子 → 提取子模式 → 定义创意方向（配色/布局/字体/质感）；2~4 个并行 Brief | 设计简报 |
| **D2 Define** | 注入品味与个性 | 独立 Critic 闭环（盲比 A/B + 参考排序）+ 可选图像增强 + 每轮内嵌产物自检 | 评审账本 + 结构清单 + 自检记录 |
| **D3 Deliver** | 收敛与减法 | 残酷减法 + AI Tells 审计 + 文案重写 | 审计清单 + 删除记录 |

**阶段纪律（硬门禁）**：

1. D1 未产出多方向简报 ⇒ 不得进入 D2；
2. D2 未同时满足「结构清单全过 + 盲比有改进（或判定已收敛）+ 人类签收」⇒ 不得进入 D3；
3. D3 审计未逐项过清单 ⇒ 不得宣称交付。

## 4. 核心机制 (Core Mechanisms)

### 4.1 种子注入：为什么必须来自模型外部

口头指令「随机一点」无效，因为模型对「随机」的理解本身就是分布的——它会产出「听起来随机」但实际高度同质的方案。

因此：种子字符串由 `scripts/generate-seed.py` 生成（模型无法预测其内容），再要求模型从种子中**提取子模式**作为设计约束（例如种子映射到色相偏移、栅格列数、字体对比度策略）。这样随机性来自系统外部，模型的职责变成「在约束下求解」而非「假装随机」。

### 4.2 Critic 分离：三条例律

| 律条 | 内容 | 违反后果 |
| :--- | :--- | :--- |
| **上下文隔离** | 每次全新上下文，不携带实现代码、迭代记录、前次批评全文 | 模型会为既有实现辩护 ⇒ 评审失效 |
| **输入最小化** | 只收当前产物（截图，无则降级文本）；盲比模式另附去标识、随机左右的上一版 | 看到代码就会评代码而不是评设计 |
| **模板固定** | 固定模板 + 必须回执版本 nonce | 防止 Critic 评的是旧版本 |

### 4.3 三信号收敛门禁

D2 完成必须同时满足：

1. **A 结构清单**：7 条 AI Tells + 层级/间距/状态/文案审计，**逐项可核验**；
2. **B 盲比改进**：上一版 vs 当前版强制选择（哪个更好 + 胜出维度），**不输出分数**；
3. **C 人类签收**。

> **绝对分数（如 x/10）仅作遥测，任何时候不得作为通过判据。** 这是本技能与「打分式评审」的根本区别：分数会产生「7 分比 6 分好」的错觉，而设计改进往往是非线性的。

### 4.4 残酷减法

D3 的第一动作是**删除**，不是增补。判据：删不掉价值说明的元素（装饰渐变 / 多余卡片 / 装饰标签）一律移除。

### 4.5 文案即占位符

AI 生成的文案一律视为排版用的 Lorem ipsum。交付前必须重写为具体、克制、口语化的人类语言；黑名单词表见 `references/ai-tells-audit.md`。

## 5. 证据契约 (Evidence Contract)

交付说明必须标注**证据三态**：

| 状态 | 含义 |
| :--- | :--- |
| **已实现** | 代码/样式已写入产物 |
| **已运行验证** | 在真实浏览器/视口中实际渲染并观察过 |
| **未验证** | 仅按设计推断，未实际运行 |

禁止把「已实现」写成「已运行验证」——这也是与 `frontend-qa-gate` 交接时的必要输入。

## 6. 角色与边界模型 (Roles & Boundaries)

| 角色 | 职责 | 不做什么 |
| :--- | :--- | :--- |
| **用户（创意总监）** | 方向选择、品味标杆、取舍裁决、最终签收 | 不写代码 |
| **主智能体（设计师）** | 种子注入、多方向探索、实现、减法、审计 | 不自评「我觉得好」 |
| **Critic（独立评审）** | 盲比、结构清单核验 | 不看实现、不给绝对分数 |
| **`frontend-qa-gate`（验收）** | 五域产物断言（响应式/状态/无障碍/浏览器/性能） | 不评美学 |

## 7. 与既有技能的接口 (Interfaces)

### 7.1 与 `frontend-qa-gate`

**分工**：本技能 D2 内的「产物自检」只做**分钟级抽查**（状态矩阵与响应式抽一两个断点），**不派发** QA Gate；完整五域验收在 D3 之后由 `frontend-qa-gate` 独立执行。

**为什么这样切**：设计迭代周期短（分钟级），每次都跑完整验收会让循环变慢 10 倍；但交付前必须过一次完整验收，否则「好看但不可用」。

### 7.2 与 `dual-round-review`

本技能产出的是**设计产物**（HTML/CSS/组件），若涉及对外发布，其代码层审查仍走 `dual-round-review`；本技能的美学判断不替代代码审查。

### 7.3 与 `goal-loop`

当设计任务作为长程目标的一部分时，由 `goal-loop` 编排；本技能的 D1/D2/D3 作为其 P3 阶段内的子流程。

## 8. 质量指标与测试策略 (Quality Metrics & Test Strategy)

**本技能没有自动化测试**——设计质量无法用脚本判定。可机械化的只有：

| 可机械核验项 | 方式 |
| :--- | :--- |
| 种子确实来自脚本 | 检查设计简报里是否记录了种子字符串与脚本输出 |
| Critic 回执 nonce 匹配 | 评审账本中 nonce 与产物版本一致 |
| 结构清单逐项有结论 | 清单每项必须填「通过/不通过 + 证据」 |
| 文案黑名单词 | `grep` 黑名单词表 |

**不可机械化的**：方向是否动人、层级是否清晰、质感是否到位——这些归人类签收。

## 9. 边界与不承诺 (Boundaries & Non-Goals)

1. **不承诺「一定好看」**：本技能提高下限（消除 AI Slop）与探索上限（外部种子），但美学判断最终归人；
2. **不替代设计系统治理**：组件库/Token 库的长期演进不在本技能范围；
3. **不覆盖可用性验收**：见 §7.1；
4. **能力门控**：无截图能力时走降级评审，**禁止假装看见了截图**——这是硬红线。

### 9.1 与文献原意的显式偏离

| 偏离 | 原因 |
| :--- | :--- |
| 增加「三信号门禁」 | 原文只说「用 Critic 迭代」，未定义何时停——无终止条件会无限循环 |
| 明确禁止绝对分数 | 原文使用偏好比较；本仓库实测发现分数会被当作通过判据滥用 |
| 与 QA Gate 显式分工 | 原文专注美学；本仓库需要与可用性验收划清边界，避免「好看但不可用」 |
