# `agy-delegation-workflow` 后台委派工作流技能架构设计书 (Architecture & Design Specification)

> **文档控制信息**
> - **文档标识**: SKILL-DES-AGY-DELEGATION-2026
> - **当前版本**: V1.0.0（首次成文，固化既有规程的架构意图）

> - **理论与实践源流**:
>   - **认知与执行分离**: 规划、契约定义与验收不得与实现由同一上下文承担（Cognition Stays Home）
>   - **零信任验收 (Zero-Trust Acceptance)**: 被委派执行体的「已完成」自述一律按未验证处理
>   - **故障注入容错 (3-Tries Rule)**: 同一根因连续三次失败即中断试错，转入降级链
>   - **宿主自适应 (Host-Adaptive Dispatch)**: 派发通道由运行宿主能力决定，而非由习惯决定

## 1. 背景与核心痛点 (Problem Statement)

把代码生产外包给后台无头执行体，收益是上下文隔离与并行吞吐，代价是**控制权的物理丢失**：产物在没有实时监督的情况下落盘。实战中暴露出四类系统性失控。

### 1.1 认知外包与越权规划 (Cognition Outsourcing)
* **表象**：后台执行体被要求「完成这个功能」，于是自行生成 `IMPLEMENTATION_PLAN.md`、`task.md` 甚至修改设计总纲，再按自己的计划写代码。
* **危害**：计划与实现出自同一上下文，等于取消了「先对齐后动手」这一层保护；计划文档还会污染仓库根目录，让后续读者误以为那是权威意图。回滚成本远高于重写。

### 1.2 虚假合规与静默降级 (Hallucinated Compliance)
* **表象**：任务要求使用既有 Mock 数据源与设计 Token，产物却自造 `DEFAULT_*` / `FALLBACK_*` 内联数组、猜测 UI 库属性名（`variant="outline"` 实为 `secondary`）、用 `alert()` 替代 `useToast()`。
* **危害**：编译通过、单测通过、审查看不出异常，但字段在真实后端上不匹配、深色模式被硬编码白色击穿、无头测试环境被 `alert` 挂起。缺陷在集成期才暴露，定位成本呈指数上升。

### 1.3 假失败掩盖真实落盘 (Phantom Failure)
* **表象**：`agy` 返回 OAuth EOF 或超时退出，前台判定失败并重跑，结果同一文件被写两遍或产生冲突。
* **危害**：进程退出码与磁盘状态解耦——超时常常发生在写完之后的收尾阶段。以退出码为唯一真相源，会同时产生「重复劳动」与「互相覆盖」两种损害。

### 1.4 状态串台与记忆污染 (Cross-Tenant Contamination)
* **表象**：无头模式没有 active workspace，hook 与 MCP 子进程的 cwd 固定在 `~/.gemini/config`；记忆库模板 `coding-agent::{gitProject}` 取不到项目名，退化为目录 basename。
* **危害**：实测曾把 6 个仓库、75 份文档、3,237 条记忆单元写进同一个 `coding-agent::config` bank。跨项目的上下文互相污染，且污染不可见——它发生在记忆层，不在代码层。

## 2. 设计基石 (Foundations)

| 原则 | 本技能的落地形态 |
|---|---|
| **认知不外包** | 架构、接口契约、数据模型、任务 Prompt、验收与入库由前台独占；后台只写实现与测试 |
| **零信任验收** | 任何产物合并前必过 6 步审查（Diff 范围 / 类型与 Lint / 失败模式 grep / 单测 / 全局构建 / 双轮终审） |
| **可复现的派发** | 任务固化为 `.agy-tasks/<task>.md` 的 7 维自包含 Prompt，同一输入可重放 |
| **失败可诊断** | 每条基础设施故障都有对应的日志位置、判别命令与降级出口，不留「重跑试试」 |
| **宿主自适应** | 优先链按宿主能力排序，同一技能在 agy 宿主与非 agy 宿主下走不同通道 |

## 3. 架构分层与职责切分 (Architecture)

```
前台智能体（规划域）                     后台执行体（实现域）
  规划 / 任务拆解        ── 7 维 Prompt ──▶  业务逻辑 / 组件 / 工具函数
  接口契约与数据模型      ── 冻结契约 ────▶  单元测试 / Mock 夹具
  测试基础设施就绪                       代码重构 / 坏味道清理
  ▼
  6 步验收 + 双轮终审 ── 通过 ──▶ 提交入库
```

### 3.1 职责矩阵

| 前台独占（严禁委派） | 后台执行（可委派） |
|---|---|
| 开发规划、阶段计划、任务拆解 | 生产代码实现 |
| 接口契约与领域模型定义 | 单元测试与集成测试编写 |
| `.agy-tasks/*.md` 任务 Prompt 编写 | 代码重构与坏味道清理 |
| 测试基础设施前置检查 | 运行本地测试并修复自身编译错误 |
| 全量审查、审计命令核验、提交入库 | 汇报执行摘要与修改文件清单 |

**SSOT 边界**：根提示词只声明协作红线与边界；派发优先级链、宿主自适应、Direct-Write 判据与任务模板全部以本技能为唯一真相源，不在全局层复制。

### 3.2 三级优先级链与降级

1. **宿主原生派发**（当前 Agent 运行于 Antigravity/agy 宿主且具备 `invoke_subagent`）——**强制**使用原生子智能体，严禁终端套娃调用 `agy`。
2. **无头命令行派发**（非 agy 宿主：Claude Code / Cursor / 纯终端 / CI）——`agy -p` + `Gemini 3.8 Flash (High)`，启动前清除全部代理变量。
3. **兜底 Direct-Write**——连续 2+ 批次中 >50% 产物需完整重写，且前台已完全掌握上下文时，前台直接编写。

第 1 级是硬约束而非偏好：在 agy 宿主里套娃起 `agy` 进程会引入第二套权限与第二份记忆库状态，是 1.4 的主要来源之一。

## 4. 关键设计决策 (Design Decisions)

### DK-1 为什么把「计划」与「实现」物理切开，而不是让执行体自规划
自规划会把对齐成本推迟到审查阶段，而审查阶段的返工是整段工作量的量级。把计划固化为前台产物（`.agy-tasks/*.md`），使「意图」在派发前即可被人类与前台下一位读者检视。**越权生成的规划文档必须立即删除**，否则它会被下一次读取当作权威。

### DK-2 为什么任务 Prompt 是 7 维自包含，而不是追加对话
后台进程无会话历史，任何未写进 Prompt 的约束都等于不存在。7 维（工作目录与目标范围、数据契约与接口模型、依赖与 API 规范、数据源与测试夹具、行为规范与架构约束、自动化验收命令、严禁事项与安全红线）是「让一个没有记忆的执行体能独立正确工作」的最小完备集。缺任一维，执行体就会用训练分布里的默认值填补——这正是 1.2 虚假合规的生成机制。

### DK-3 为什么强制清代理、强制 `--add-dir`
代理变量污染会让 `agy` 报 `proxyconnect ... connection refused` 或区域阻断，表象是模型故障，实质是网络路径错误；`--add-dir "$PWD"` 解决的是记忆库归属（1.4）。两者都不是「最佳实践建议」，而是已知会把结果从「正确」变成「静默错误」的开关——静默错误比报错昂贵得多。

### DK-4 为什么假失败要人工判别而不是自动重试
退出码与磁盘状态解耦（1.3）。自动重试在「已落盘」时会覆盖或冲突，在「未落盘」时浪费一次长任务。判定顺序固定为：`git status -s` 看落盘 → 跑单测看功能 → 通过即视为成功并进入审查。把「是否成功」的定义从进程退出码改为**产物可验证状态**。

### DK-5 为什么验收是固定 6 步而不是「跑一下测试」
每一类失败模式对应一条独立证据：Diff 范围查越权与收敛、类型与 Lint 查接口幻觉、grep 审计查自造 Fallback 与调试残留、单测查行为、全局构建查类型泛化断裂、双轮终审查架构回归。它们互不覆盖——单测全绿仍可能含 `"use client"` 缺失（jsdom 不报）或硬编码颜色。合并成「跑测试」会漏掉其中四类。

### DK-6 为什么同文件任务必须合并、build 必须串行
两个任务改同一文件并行执行必然竞态，且失败现场无法归因；全局构建是 CPU 与 I/O 密集操作，并行只会拉长墙钟时间并放大内存峰值。并行度只在「无文件交集」与「非构建」两个维度上释放。

## 5. 失败模式与防护映射 (Failure Modes)

| 失败模式 | 判别证据 | 防护位置 |
|---|---|---|
| 自造 Fallback 数据 | `grep -rn 'DEFAULT_\|FALLBACK_'` 排除 import/mock | `references/failure-modes-audit.md` §1 |
| 编造组件 API | 对 UI 库属性名 grep 与官方签名比对 | 同上 |
| 硬编码颜色 / `alert()` | `text-white`、`bg-white`、`alert(` grep | 同上 |
| `"use client"` 缺失 | `grep -rL '"use client"' ... \| xargs grep -l 'useState\|onClick'` | 同上 |
| 代理污染 / 区域阻断 | `cli-*.log` 中 `proxyconnect`、`location is not supported` | `references/infrastructure-troubleshooting.md` §1 |
| OAuth EOF 假失败 | `git status -s` 落盘证据 | 同上 §2 |
| 记忆库串台 | bank 名退化为 `coding-agent::config` | SKILL.md §2 记忆库归属 |
| 执行体越权写文档 | `git diff --stat` 出现 `task.md`/`IMPLEMENTATION_PLAN.md` | SKILL.md 红线原则 |

## 6. 边界与已知上限 (Boundaries & Known Limits)

* **本技能不定义「做什么」**：任务拆分质量取决于前台的规划能力与 `writing-plans` 类技能，本技能只保证「怎么派、怎么验」。
* **不适用于交互式决策**：任何需要用户澄清的环节必须留在前台，后台无法发起澄清。
* **假失败判别依赖单测存在**：若目标模块没有可运行的测试，「跑单测看功能」这条判据退化为不可用，只能退回人工读 Diff。
* **优先级链是能力判断，不是环境嗅探**：宿主是否具备 `invoke_subagent` 需要显式确认；自动嗅探失败时会退回套娃调用，属已知故障路径。
* **6 步验收不覆盖设计缺陷**：它可以证明「实现了被要求的东西」，不能证明「要求的东西是对的」——后者属双轮终审的职责边界。

## 7. 与其它技能的协作 (Interfaces)

* `writing-plans`：任务拆解与计划文档规范的来源，本技能在 §1 要求优先激活。
* `dual-round-review`：6 步验收的最后一步，负责架构级回归与阻断裁决。
* `goal-loop`：长程任务的状态机与检查点；本技能是其中一个执行通道。
* `doc-governance`：产物涉及的契约/模型变更按 Diátaxis 与 ADR 规范联动同步。

## 8. 演进方向 (Roadmap)

1. **落盘判据自动化**：把 `git status -s` + 单测的假失败判别封装进 `dispatch-agy.py`，消除人工漏判。
2. **失败模式清单外置**：`failure-modes-audit.md` 目前绑定 Next.js/React 生态，需按技术栈分区，避免在其它栈上产生无关 grep 噪音。
3. **bank 归属硬校验**：派发前断言记忆库名与本仓库一致，不一致即拒绝派发，把 1.4 从「已修复」升级为「不可能发生」。
