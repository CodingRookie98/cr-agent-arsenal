## 1. 背景与业务痛点 (Why)

### 1.1 现象：审查报告全文从未落盘

`dual-round-review` 的两轮提示词模板已定义完整的报告输出契约——R1 需产出「第一性原理分析 / 红队攻击路径推演 / 潜在缺陷清单」，R2 需产出「元审查质询 / 终审裁决明细表 / 放行结论」。但**技能全流程没有任何一步要求把子智能体返回的报告原文写入磁盘**。

[技能铁律 5](../../skills/dual-round-review/SKILL.md) 只规定写入「每轮结论」——实际落盘的是 [步骤 1.5](../../skills/dual-round-review/SKILL.md) 定义的 8 字段摘要锚点，且该锚点所在目录已在 [.gitignore](../../.gitignore) 中被忽略。

**实证**（本仓库 2026-09-21 `frontend-qa-gate` 交付的审查产物）：
- 摘要文件中自述：`> 全文见会话记录；本文件供 Delta R1/R2 与结项引用。`
- 该交付唯一进入版本库的审查内容，是[实施计划](../../docs/project/plans/2026-09-21-frontend-qa-gate.md) 中**手工重写**的摘要表格，标注「报告：子智能体 `f3a5d30b`」——一个会话结束即失效的句柄。

### 1.2 后果：三类受众同时受损

| 受众 | 受损方式 |
| :--- | :--- |
| **R2 元架构师子智能体** | R2 模板的 `[INSERT_ROUND_1_REPORT]` 槽位依赖主智能体**手工内联转录** R1 全文——转录即失真，且无任何机制可校验转录的完整性 |
| **人类参与者** | `git clone` 后**什么都看不到**：审查是交付准入的核心凭据，却不可审计、不可在 PR 中引用、不可跨机器复盘 |
| **编排者（`goal-loop`）** | 阶段 4 的放行判定只能消费摘要字段，无法机械核验「终审裁决」与报告原文是否一致 |

### 1.3 根因：两类生命周期不同的产物被塞进了同一个容器

| 维度 | ① 运行时状态 | ② 交付凭据 |
| :--- | :--- | :--- |
| 内容 | 恢复锚点、迭代计数、Previous Blockers | R1/R2 报告全文、终审裁决 |
| 生命周期 | 一次审查循环（小时级） | 交付审计期（长期） |
| 变更频率 | 高频改写 | 一次写入，只读 |
| 消费者 | 主智能体 / Delta 恢复 | 人类 / R2 / 编排者 |
| **可否重建** | **可**（从仓库状态重建） | **不可**（原文只有那一次生成） |
| 社区惯例位置 | 隐藏目录 + `.gitignore` | 版本库（同 ADR） |

现状把 ② 存进了 ① 的容器：一份**不可重建**的凭据，被放进了「可重建、被忽略」的目录，于是全文干脆没有落盘这一步。

### 1.4 旁证：这是武器库的共性缺口

`frontend-qa-gate` 已具备 [报告结构机械校验器](../../skills/frontend-qa-gate/scripts/check-qa-report.sh)，却同样**未规定报告落位**。整个武器库缺失的是「报告产物的持久化落位层」，本 RFC 以 `dual-round-review` 为试点。

## 2. 目标与非目标 (Goals & Non-Goals)

### 2.1 核心目标 (Goals)

- [ ] **G1 报告全文零损耗落盘**：R1 / R2 / Delta 各轮的报告原文逐字归档，禁止以摘要替代全文。
- [ ] **G2 归档进入版本库**：`git clone` 后人类可直接阅读，子智能体可按路径寻址。
- [ ] **G3 两层职责分离**：运行时状态继续留在被忽略的 `.review-context/`，交付凭据移入被跟踪的归档根。
- [ ] **G4 机械门禁**：新增报告校验脚本，使「报告结构完整、两轮稳定 ID 对齐、指纹与登记一致」可机械证明。
- [ ] **G5 消除转录失真**：R2 输入由「主智能体内联转录」改为「归档文件路径 + SHA256 指纹」，宿主无读文件能力时降级内联并显式标注。

### 2.2 明确非目标 (Non-Goals / 防蔓延红线)

- **不**改动 `.review-context/` 的 `.gitignore` 状态（运行时状态的忽略策略是正确的）。
- **不**回填历史审查报告（原文已不可恢复，仅有摘要，回填无实质意义）。
- **不**实现自动裁剪 / 保留期策略（登记为默认假设，后续按需立项）。
- **不**引入报告格式转换（HTML / PDF）与报告可视化。
- **不**为 `frontend-qa-gate` 或其他技能同步落位改造（本 RFC 只做 `dual-round-review` 试点；共性沉淀留待验证后另行提案）。
- **不**改变审查模式语义（Full / Light / Delta）、裁决分级标准与派发预算。

> **验收口径 (Acceptance Criteria)**
> - **验收人**: 王辉（需求方）
> - **验收场景**:
>   1. 对任一次真实双轮审查，`git status` 显示归档目录为**新增且被跟踪**的文件；
>   2. 打开归档目录，可见 R1 与 R2 的**完整报告原文**（含攻击路径推演与裁决明细表全部行），非摘要；
>   3. 运行 `check-review-report.sh <归档目录>` 退出码为 0；
>   4. 人为篡改报告中一行后重跑脚本，退出码非 0（指纹校验生效）。
> - **明确不验收项**: 历史交付（`frontend-qa-gate` 等）的报告回填；报告体量的自动清理；其他技能的落位改造。
> - **口径冲突裁决人**: 王辉

## 3. 核心设计与契约草案 (How - Technical Draft)

> 本节为草案，定案前严禁作为生产基线直接引用。

### 3.1 三层职责分离拓扑

```text
① 运行时状态层（保持现状 · 高频易变 · .gitignore 不动）
   .review-context/review-<baseline-sha>.md
     ├── 既有 8 字段（模式/基线/轮次/迭代计数/Previous Blockers/结论/裁决/统计）
     └── 新增「归档索引」段：归档根、报告文件清单、各报告 SHA256、实际归档根（宿主覆盖时）

② 交付凭据归档层（新增 · 一次写入 · 进版本库）
   docs/project/reviews/<YYYY-MM-DD>-<slug>/
     ├── README.md                    归档索引（轮次台账 + 报告清单 + 指纹 + 终审裁决）
     ├── r1-<base7>..<head7>.md       R1 报告全文（逐字）
     ├── delta-r1-<base7>..<head7>.md Delta R1 报告全文（逐字）
     ├── r2-<base7>..<head7>.md       R2 终审裁决书全文（逐字）
     └── delta-r2-<base7>..<head7>.md Delta R2 报告全文（逐字）

③ 机械门禁层（新增）
   skills/dual-round-review/scripts/check-review-report.sh
```

### 3.2 归档根的可移植性契约

技能是可分发资产（`npx skills add` 会装入第三方项目）。因此：

- **推荐默认归档根** = `docs/project/reviews/`；
- **宿主优先**：宿主项目若已有既定的审查记录规范（既有 `reviews/` 目录、或 doc-governance 变体），**以宿主规范为准**；
- **必须登记**：实际使用的归档根写入运行时锚点的「归档索引」段，使编排者与后续会话可寻址；
- 措辞风格对齐宿主既有约定：`contexts/AGENTS.md` 对计划文档的表述为「统一归档至标准目录（**推荐** `docs/project/plans/`）」。

### 3.3 命名规范

| 对象 | 规则 | 示例 |
| :--- | :--- | :--- |
| 归档目录 | `<交付单元首次审查日 YYYY-MM-DD>-<交付单元 slug>` | `2026-10-04-review-report-archive` |
| 轮次报告文件 | `<轮次标记>-<base7>..<head7>.md` | `r1-940e0f3..a1b2c3d.md` |
| 轮次标记 | `r1` / `r2` / `delta-r1` / `delta-r2` | `delta-r2-940e0f3..e4f5a6b.md` |
| 索引文件 | `README.md` | — |

- **一个交付单元一个目录**：同一交付的 Delta 再循环各轮**共享同一目录**，不因跨天而分裂；目录名日期取该交付**首次审查日**（消除跨天漂移）。
- `slug` 由主智能体按交付单元命名，与实施计划文档名对齐（如计划为 `2026-10-04-review-report-archive.md`，则 slug 为 `review-report-archive`）。

### 3.4 归档索引 (README.md) 契约

```markdown
# 审查归档 · <交付单元名称>

- **交付单元**: <slug>
- **归档根**: docs/project/reviews/<YYYY-MM-DD>-<slug>/
- **审查模式**: [full | light | delta]
- **当前迭代计数**: [n/3]
- **终审裁决**: [🔴 阻断交付 | ✅ 准予交付 | 未定]

## 轮次台账
| 轮次 | 基线 | 派发句柄 | 报告文件 | SHA256(前 12 位) | 结论 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| R1 | `940e0f3..a1b2c3d` | <子智能体句柄> | `r1-940e0f3..a1b2c3d.md` | `3f9a734b21c4` | 🔴 3 / 🟡 9 / ⚪ 1 |
| R2 | `940e0f3..a1b2c3d` | <子智能体句柄> | `r2-940e0f3..a1b2c3d.md` | `7b29e7a4cef1` | 🔴 1 阻断 |

## 待办与后续轮次
- [ ] <由 R2 裁决衍生的待办或下一轮基线>
```

### 3.5 机械门禁校验项

`check-review-report.sh <归档目录>` 校验（退出码 0 = 通过，1 = 缺陷，2 = 用法错误）：

1. **索引齐备**：`README.md` 存在，且含「交付单元 / 归档根 / 终审裁决」三个必需字段；
2. **报告存在性**：轮次台账中登记的每一个报告文件**实际存在**且非空；
3. **指纹一致**：台账登记的 SHA256 前缀与文件实际计算值一致（防事后篡改与转录漂移）；
4. **R1 结构完整**：每份 R1 报告含 5 个必需区块（第一性原理 / 运行时与 SSR·条件 / 红队攻击路径 / 潜在缺陷清单 / 结论概要）；
5. **R2 结构完整**：每份 R2 报告含 3 个必需区块（元审查质询 / 裁决明细表 / 放行结论）；
6. **稳定 ID 对齐**：R2 裁决明细表出现但 R1 缺陷清单中不存在的稳定 ID 视为缺陷（两轮必须机械对齐）；
7. **纵深层校验**：必需区块不得**仅**出现在围栏代码块内（防围栏伪造，沿用 `check-qa-report.sh` 的已验证手法）。

### 3.6 关键接口改造

| 接口 | 现状 | 改造后 |
| :--- | :--- | :--- |
| R2 输入 R1 报告 | `[INSERT_ROUND_1_REPORT]` 由主智能体内联转录全文 | 给**归档文件路径 + SHA256**，要求 R2 读取原文并核验；宿主无读文件能力时降级内联全文，并在报告中标注「内联降级」 |
| Delta 再循环恢复 | 从锚点摘要读 `Previous Blockers` + 迭代计数 | 同上，并新增从归档 `README.md` 轮次台账读取上一轮报告路径 |
| 落盘动作 | 步骤 2/3 只写锚点字段 | 步骤 2/3 增加「归档报告全文 + 登记指纹」动作；归档完成后方可进入下一步骤 |

### 3.7 写入责任边界（安全约束）

- **默认**：主智能体在收到子智能体真实返回后**逐字写盘**，并计算 SHA256 登记至锚点与索引；
- R1/R2 子智能体的 **Read-Only 约束保持不变**（不修改工作树、分支与索引）；
- 由此「转录失真」由**指纹登记**兜底：任何事后发现的不一致都可被 3.5 的门禁机械检出。

### 3.8 异常分支与降级策略

| 异常 | 处置 |
| :--- | :--- |
| 宿主无 `docs/` 结构 | 按 3.2 使用宿主规范或回退至推荐默认；实际归档根登记至锚点 |
| 归档目录已存在（Delta 再循环） | 追加轮次台账行，**不覆盖**既有报告文件；同名冲突视为基线漂移缺陷 |
| 报告体积过大（超长 Diff 全量内联） | 报告落盘不截断；提示词侧维持既有的 800 行 Diff 内联阈值与按需调阅授权 |
| 报告落盘失败（磁盘/权限） | 按 `goal-loop` 的 `host-adapters.md` §5 收口：记录中断原因，**禁止**在无归档的情况下宣布审查通过 |

## 4. 备选方案权衡与争议焦点 (Alternatives & Trade-offs)

### 方案 A（本提案选定）：两层分离 + `docs/project/reviews/`

- **核心理念**：按生命周期与可否重建切分，运行时状态保持社区惯例的隐藏目录，交付凭据进版本库。
- **优势**：受众诉求各自闭合；复用 `doc-governance` 既有门禁（断链扫描、健康体检、索引、修订历史治理）；与宿主 `goal-loop` 的「`.goal-loop/` 高频态 + `docs/project/plans/` 真相源」既有分层同构。
- **已知代价**：审查报告进入知识库目录体系，需要在治理规程中明确其象限归属；报告体量长期累积需要后续保留策略。

### 方案 B（未采纳）：顶层 `reviews/` 独立目录

- **核心理念**：与 `docs/` 平级，职责最清晰，不污染 Diátaxis 知识库。
- **未采纳理由**：脱离 `doc-governance` 的全部门禁与索引体系——报告将不受断链扫描、健康体检与 `docs/index.md` 覆盖，需要另行建立并维护一套治理规则，投入产出比劣于方案 A。本仓库既有的「技能规定 `docs/` 落位」先例（`goal-loop` → `docs/project/plans/`）也支持方案 A。

### 方案 C（未采纳）：`.review-context/` + `.gitignore` 负向白名单

- **核心理念**：改动最小，复用社区惯例的隐藏目录，仅用白名单让归档文件被跟踪。
- **未采纳理由**：「忽略整个目录 + 逐文件白名单」的规则脆弱——新增轮次报告若忘记加白名单即静默丢出库外，把**持久化可靠性**建立在一个易漏的人工步骤上；且运行时状态（高频改写）与交付凭据（只读）混居同一目录，语义仍混淆。

### 争议焦点与裁决

| # | 争议 | 裁决 |
| :--- | :--- | :--- |
| 1 | 社区惯例（`.agents/`、`.review-context/` 隐藏目录）是否应作为归档位置？ | 该惯例服务的是**运行时状态与配置**，且默认被 `.gitignore` 忽略；本仓库 `.agents/` 系 `install.py` 生成的安装态视图，放审计凭据存在被重建的语义冲突。**裁决**：隐藏目录继续承担 ①，凭据另立 ②。 |
| 2 | 硬编码 `docs/` 是否损害技能可移植性？ | 是潜在风险。**裁决**：措辞改为「推荐默认 + 宿主规范优先 + 实际归档根登记」，对齐宿主既有约定风格。 |
| 3 | 是否回填历史报告？ | **否**。原文已随会话销毁，仅有摘要，回填无实质意义。 |
| 4 | 是否需要报告裁剪/保留策略？ | 本期**不做**，登记为默认假设，待体量成为实际问题后另行立项。 |

## 5. 术语表与易歧义对齐 (Glossary & Terminology Alignment)

> ⚠️ **本段是评审的前置条件（术语先行）**。范围以「核心术语 + 易产生歧义」为界，禁止扩张为全量词表。

### 5.1 核心术语定义 (Core Term Definitions)

| 术语 | 定义（一句话，可判定） | 范围 / 边界 | 不包含 (Excludes) |
| :--- | :--- | :--- | :--- |
| **审查报告全文** | 审查子智能体返回的、未经主智能体改写或压缩的**逐字原文** | 含 R1/R2/Delta 各轮全部区块与表格行 | 主智能体手工重写的摘要表格、会话内的转述 |
| **审查记录锚点** | 落盘于 `.review-context/review-<baseline-sha>.md` 的**短周期运行时状态**文件（8 字段 + 归档索引段） | 供 Delta 再循环恢复轮次与迭代计数 | 报告全文；长期审计凭据 |
